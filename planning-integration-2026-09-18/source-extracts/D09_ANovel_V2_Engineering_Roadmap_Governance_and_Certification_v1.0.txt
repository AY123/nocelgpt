原则：代码可以从零开始，认知、证据和失败经验不能从零开始。

1. 总原则：先证明生产真值，再扩功能
V2 第一阶段绝不复制 V1 的“模块数量驱动”。开发顺序必须从 Domain/State/Contract/Workflow 向上生长，直到单章事务闭环和双 Genre 隔离通过认证，才允许扩大 Agent、UI、Corpus 和商业预测。

9. 30章出口标准
维度
必须满足
Genre
Urban / Fantasy cross-contamination = 0 major
Canon
身份/时间/世界硬事实重大冲突 = 0
Commit
废稿、失败稿、修订前稿不污染 Canon
Resume
随机 kill ≥5 次恢复成功且不重复 side effect
Evidence
每章 body/contract/context/validation/changeset/receipt 可追溯
Quality
关键章人工复盘可接受；代理分不作为唯一结论

10. 100章出口标准
后 50 章相对前 50 章不存在持续性质量坍塌。
Major unresolved promise/continuity violations 在阈值内且均可解释。
成本/重试/缓存/人工干预分钟数可报告。
事实回流确实改变下一章 Contract/Context，而不是只写数据库无人消费。
同一 run 可重放核心决策链，版本漂移被明确阻断。
11. 项目管理原则
README 只做事实入口；Roadmap 只做计划；ADR 记录不可逆/高成本决策。
“完成”必须绑定可执行测试/真实消费者/运行证据。
任何市场/模型相关假设必须注明时间、样本和校准状态。
每个 Sprint 结束必须删除或归档无消费者原型，防止长期腐化。
12. 开工顺序（推荐）
建立新仓与 CI/secret scan/architecture guard。
实现 Genre Ontology + Urban/Fantasy Pack skeleton。
实现 Canon core + event/snapshot + transaction API。
实现 Chapter/Scene Contract 与 frozen ContextArtifact。
接入单一 Writer/Extractor/Validator，不做多 Agent。
完成 1 章→10 章→30 章双 Genre 认证。
再引入多模型、Repair、Human calibration。
最后扩 Reference/Corpus、100章、平台反馈。
