核心裁决：ANovel V2 不应被设计成“更多 Agent 的 AI 写作系统”，而应被设计成“以 Genre Constitution + Canonical Narrative State + Contract + Durable Workflow + Verification 为内核的商业网文生产操作系统”。
V1 最大的价值不是它已经完成了多少功能，而是它暴露了真实失败模式：类型泄漏、人物/时间/事实漂移、状态多源、评审信号未校准、工作流与证据链割裂、模块不断增加但生产真值不稳定。V2 的设计必须把这些失败转化为不可违反的架构约束和回归基准。
公开项目与研究说明，长篇 AI 创作的成熟方向正在趋同：Story/Codex 结构化知识、Accepted/Committed Content 才能更新 Canon、动态分层规划、显式世界状态、场景级状态转换、连续性验证、局部修复、Durable Execution、Human-in-the-loop。ANovel V2 应在这些共识之上进一步解决“中文商业网文类型治理 + 商业留存 + 百万字生产 + ReaderSignal 校准”。
0.1 一句话产品定义
ANovel V2 = Commercial Web-Novel Production Operating System
它以类型宪法、叙事事实状态、分层规划、章节/场景契约、状态转换验证、多模型执行、质量与商业评估、人工校准和真实读者反馈为核心，使 AI 能够长期、稳定、可审计地生产几十万至数百万字的商业网文。

0.2 本文最终 Architecture Decision
V2 采用全新代码库/新主干思路；V1 只迁移验证过的知识、数据模型思想、失败样本、测试与部分纯净组件。
Genre 从“字符串/Prompt 标签”升级为可执行的 Genre Constitution + Policy Pack，并在规划、上下文编译、生成后验证三个阶段强制执行。
Canonical Narrative State 是唯一小说真值；正文草稿、Reviewer 结论、预测信号都不能直接修改 Canon。
只有 Committed Chapter/Scene 触发 Canon State Transition；失败一律回滚或进入 Revision，不允许 warning 后继续污染状态。
工作流采用显式 Stage Graph + Durable Execution；模型调用是 Activity/Worker，不拥有长期状态。
Context 不是临时拼 Prompt，而是可测试、可哈希、可复现的 Context Compiler 输出。
确定性规则、语义一致性、叙事质量、商业质量、人工判断分层治理；未校准 Judge 不得拥有最终发布权。
规划采用动态分层结构：Series → Volume → Arc → Chapter → Scene；远期抽象、近期具体，可根据已提交 Canon 局部重规划。
Corpus Intelligence 只提供抽象证据与模式，不直接把参考作品连续原文喂给生产 Writer；原创性是架构级约束。
V2 开发按“1章闭环 → 10章 → 30章双类型 → 100章 → 真人盲评 → 真实平台”推进，禁止用新增模块替代生产验证。

1.2 V1 不应带入 V2 的结构
Agent / Reviewer / Schema 随需求不断新增，而没有稳定 Domain Ownership。
“有 Story Bible”但 Genre、人物、时间和事实仍可能在运行时漂移；说明约束没有变成可执行生产政策。
Contract、Continuity 或 State 缺失时存在 fail-open 路径；生产模式必须改为 fail-closed。
运行时出现小说特定硬编码、placeholder provenance、默认关闭的关键安全集成；V2 核心层禁止作品专用逻辑。
多个 verdict / report / pipeline decision 同时表达“是否可继续”，造成权威状态不唯一。
大包/大目录吸收越来越多职责，工作流、评估、实验、序列化、报告混杂。
Judge、模拟读者或商业预测在未被真人/平台校准前容易被误当作真值。
CI、依赖锁定、Secret Scan、Architecture Guard 不够早，导致“本地通过”不能自动成为仓库门禁。
文档、历史实验、生成产物、运行证据与源码边界混杂，增加认知噪声。

2. 外部参考架构与竞争设计：逐项拆解
本节只吸收“被公开资料明确展示”的能力。对商业产品不推断其内部实现；对研究论文不把实验结果直接等同于商业可用性。每个对象都给出：可借鉴、不应借鉴、V2 改良、最终 Architecture Decision。
2.1 Novel Studio AI（YfengJ）
Local-first 长篇工作台；Accepted Chapter 才更新 summary、character state、graph triples、timeline events 与 memory。
可借鉴
不应借鉴
V2 改良方案
• Accepted Chapter = Canon Commit 的边界非常清楚。• Context Pack 把 Story Bible、Style、Arc、Chapter、Recent Summary、Character State、Graph Facts、Timeline、Forbidden Contradictions 组合成显式输入。• 结构化输出使用 schema validation；本地数据库承载稳定记忆。
• 不应直接复制其较轻量的数据模型作为百万字商业网文的最终模型。• 不要把 hybrid retrieval 当成“事实正确”的替代品；检索只能提供候选上下文。• 不应把 UI/本地工作台形态等同于 V2 的核心架构。
• 把 Accept/Commit 扩展为事务式 Chapter/Scene Commit；写入前必须通过 Genre、Canonical State、Transition、Quality Gate。• Context Pack 升级为可哈希 Context Compiler Artifact，并记录选择原因、优先级、token budget 和裁剪日志。• Character State/Graph/Timeline 统一进入 Canonical Narrative State + Event Ledger。

最终 Architecture Decision
ADR：正式采用“Draft Never Mutates Canon；Commit Is the Only Canon Mutation Boundary”。

2.2 NovelForge / novel-agent（hzhang092）
面向中文网文的本地 AI 创作工作台，强调 Domain/Application/Pipeline/Provider/Storage 分层与 Human-in-the-loop。
可借鉴
不应借鉴
V2 改良方案
• Domain 与 Provider 分离，适合避免模型耦合。• Novel Bible、character intent、writer、reviewer、fact extractor、state updater 的职责链清楚。• 作者作为 editor-in-chief，AI 是执行者而不是事实所有者。
• 不要复刻“每种任务一个 Agent”的增长路径。• 早期项目接口仍在变化，不能把具体 API 结构当成熟标准。• 用户审批流不应成为系统一致性的唯一保障，硬约束必须自动执行。
• 保留 clean architecture 思想，但将 Agent 改名为 stateless worker/capability role。• 把审批与状态转换显式化：Proposed → Validated → Approved/AutoApproved → Committed。• 所有 Provider 通过 Model Gateway 暴露能力与成本，不进入 Domain。

最终 Architecture Decision
ADR：采用 Domain / Application / Workflow / Infrastructure 边界；Worker 无长期状态。

2.3 novel-studio（Xiaoyangy）
开源、本地优先、可恢复的长篇小说生产引擎；先推演世界和角色，再封存窗口计划；审核通过后才进入正史。
可借鉴
不应借鉴
V2 改良方案
• 角色不只跟随主角：维护当前目标、压力、资源、误判、知识边界、同时间线行动。• 封存规划窗口、再渲染正文，有利于把因果推演与表述分开。• 正文可以是单 POV，但世界状态需要记录“屏幕外”关键角色活动。
• 不要让每个角色长期运行成自治 Agent，以免成本和状态复杂度爆炸。• 不应把短窗口推演当成全局规划替代品。• “角色推演”结果仍必须服从 Genre/World/Arc Constitution。
• 引入 Character Stage Record / Knowledge Boundary / Offscreen Activity，但作为 Canon State 的一部分。• 增加 Simulation Sandbox：可推演但不写 Canon；只在 Chapter Contract 通过后提交。• 角色 Worker 按需实例化、无状态，状态属于 Canon。

最终 Architecture Decision
ADR：人物自主性建模为 state + goal + knowledge + constraints，而不是永久 Agent 身份。

2.4 DOME（NAACL 2025）
Dynamic Hierarchical Outlining + Temporal Knowledge Graph，用动态分层大纲与记忆增强缓解长篇固定大纲和时间冲突。
可借鉴
不应借鉴
V2 改良方案
• 远期规划抽象、近期规划具体；规划与写作循环耦合而不是一次性冻结全书。• Temporal KG 作为长期记忆与冲突分析手段。• 明确提出 rigid outline 在长篇生成中的局限。
• 不要把论文中的实验长度直接外推到百万字商用。• Temporal KG 不能替代权威 Canon；图只是 Canon 的一种索引/投影。• 动态重规划不能偷偷改写已经承诺给读者的核心 Promise。
• 采用层级规划：Series Vision → Volume → Arc → Chapter → Scene。• 重规划必须基于已提交 Canon、Reader Promise 和不可逆事件，产生版本化 Plan Diff。• Temporal graph 作为查询投影，权威仍为 Canon Event Ledger + Snapshot。

最终 Architecture Decision
ADR：规划是版本化、局部可重规划的层级计划，不是一次性 1000 章静态大纲。

2.5 ConWriter（2026）
Transition-constrained、stateful、scene-level 长篇生成；通过 symbolic state、风险信号和 localized repair 在错误扩散前处理。
可借鉴
不应借鉴
V2 改良方案
• “生成文本”改写为“从 State N 完成 Required Transition 到 State N+1”。• 按风险选择验证深度，避免每一步都高成本全量评审。• Localized repair 优于整章无限重写，能减少次生破坏。
• 不要把 symbolic state 简化成几个字段；网文需要关系、知识、承诺、资源、经济、能力等多账本。• 研究基准的 3k/6k/12k 级实验不能替代真实 30/100 章验证。• 不应让 LLM 自己声明 transition 成功；关键转移需要独立验证。
• 定义 TransitionSpec / ActualTransition / Delta Validator。• 硬事实走 deterministic validator，软叙事走 semantic evaluator。• Revision 采用 patch-first、span-scoped、protected facts、revalidate。

最终 Architecture Decision
ADR：Scene/Chapter 的一等输出包含 Narrative Delta；正文只是对 Delta 的表现。

2.6 MAGNET + ATLAS（2026）
角色目标驱动的共享世界状态生成 + scene graph verification；100 页实验显示相对基线减少标注冲突/幻觉。
可借鉴
不应借鉴
V2 改良方案
• 角色行动来自 persona + goal + shared world state，而非仅从主角视角续写。• 生成与验证分离；ATLAS 用图表示检查跨 scene 状态。• 明确将 world state 作为多角色协调中心。
• 不要照搬多 Agent 常驻架构。• 论文结果依赖实验设置，不能当商业网文质量证明。• Graph representation 不是唯一存储模型。
• 保留共享世界状态、目标和 persona grounding；角色 worker 按 scene/arc 临时执行。• Graph verifier 成为 Canon Projection Validator 之一。• 把“人物知道什么/能做什么/想做什么”明确分离。

最终 Architecture Decision
ADR：共享世界状态中心化，智能执行分布化；状态不属于 Agent。

2.7 ConStory-Bench（ACL 2026）
长篇一致性 Benchmark，覆盖 Characterization、Factual Detail、Narrative Style、Timeline & Plot、World-building 等 5 类 19 子类。
可借鉴
不应借鉴
V2 改良方案
• 一致性错误需要分类 benchmark，而不是只看综合分。• 可以把 V1 的真实失败变成定制 benchmark。• 评估应覆盖 continuation/generation/expansion/completion 等不同任务。
• 不要只依赖自动 Checker；它仍可能漏报和误报。• 公开 taxonomy 需要为中文网文增加商业与类型特有错误。• Benchmark 通过不代表文本好看或能卖。
• 建立 ANovelBench：Consistency + Genre + Commercial + Long-Arc + Recovery。• 每次架构变更必须跑固定红队故事集。• Benchmark 输出与 Human/ReaderSignal 分层，不混为一个总分。

最终 Architecture Decision
ADR：回归基准是一等产品资产，与源码同等受版本治理。

2.8 Novelcrafter
成熟 AI 辅助写作平台；Codex 维护人物、地点、Lore 并跨书共享；支持自定义提示与多模型/本地模型。
可借鉴
不应借鉴
V2 改良方案
• Codex 的“可编辑、可链接、跨书共享”是优秀产品体验。• Model/provider 不锁定，用户可选择外部或本地模型。• 规划、写作、审阅在同一产品中协同。
• 不要把 Codex 的人类可读知识库直接当机器 Canon。• 不要让 Prompt 自定义绕过生产政策。• 其核心定位是写作平台，不应照搬其 Human-assist 工作流作为自动生产内核。
• 把 Codex 分成 Authoring View 与 Canon Machine Model；UI 编辑通过 Change Proposal 进入 Canon。• Model Gateway 保持 provider-neutral。• Prompt customization 受 Policy 和 Schema 约束，不能越权。

最终 Architecture Decision
ADR：产品层允许灵活编辑，核心层只接收经过验证的结构化 ChangeSet。

2.9 Sudowrite
Story Bible 将 Braindump、Genre、Style、Synopsis、Characters、Worldbuilding、Outline、Scenes、Draft 串成创作层级；Scene 是章节基本构件。
可借鉴
不应借鉴
V2 改良方案
• Scene-first 比直接整章生成更容易控制位置、时间、人物和目标。• Story Bible 字段之间存在清楚的信息依赖。• 产品交互对作者非常友好。
• Genre 主要作为生成上下文，仍不是强制执行的 policy。• 不要让长篇真值停留在可自由编辑的文本字段。• 不要把一个 Story Bible 文本块当作全部上下文来源。
• 保留 Story → Outline → Scene → Prose 的可解释层级；加入 Genre Constitution 和 Canon State。• Scene Contract 成为生产最小控制单元；Chapter 是事务提交单元之一。• 所有 Story Bible 编辑产生 schema-valid Change Proposal。

最终 Architecture Decision
ADR：Scene 是生成/修复最小单元，Chapter 是商业阅读与主要提交单元。

2.10 NovelAI
Lorebook 将人物、地点、物品、派系等信息按触发条件注入 context；强调 context budget 和局部控制。
可借鉴
不应借鉴
V2 改良方案
• 按相关性激活知识，而不是每章把整本 Bible 塞进 prompt。• Context injection 需要优先级、触发、位置与预算。• 支持局部生成控制的思想。
• 不要把关键词触发当真正检索/推理。• Lorebook 内容不等于权威事实状态。• 不要依赖 token context 承担长期记忆。
• 建立 Context Compiler：规则选择 + graph/entity retrieval + temporal relevance + arc relevance + token budgeting。• Context Artifact 记录 included/excluded reasons 和 hashes。• Canon 事实从数据库/事件账本读取，不从模型历史推测。

最终 Architecture Decision
ADR：Context 是编译产物，不是聊天历史。

2.11 Temporal / LangGraph（非小说域基础设施）
Durable Execution、持久化状态、失败恢复、Human-in-the-loop、replay 是长时 AI Workflow 的成熟基础设施。
可借鉴
不应借鉴
V2 改良方案
• 工作流状态与 Activity 副作用分离。• 失败后从持久历史恢复，而不是手写大量 checkpoint 分支。• 幂等、重放、暂停/人工审批是核心能力。
• 不要让工作流框架定义小说 Domain。• 不要把任意 LLM 调用直接写进可重放的确定性 workflow 逻辑。• 不要过早绑定某一家运行时；先定义 Workflow Port。
• V2 设计 DurableWorkflowPort，默认评估 Temporal；轻量部署可适配 LangGraph。• 模型/API/文件写入作为 Activity，带 idempotency key 与 persisted result。• Run Manifest 从“报表”升级为执行事实。

最终 Architecture Decision
ADR：不再自制不完整的长时任务可靠性；采用成熟 durable execution 模式。

3. V2 仍需自己补充的关键能力（公开项目普遍没有完整解决）
综合 V1 和外部项目后，ANovel V2 真正形成差异化的不是“再多几个智能体”，而是下面这些跨领域能力。它们应在架构阶段明确，否则项目会再次在功能开发中补丁式生长。
能力
V2 定义
Genre Constitution
把类型定义为世界允许性、能力系统、现实度、技术水平、冲突模型、套路、语言/节奏、禁区、商业承诺、混合类型规则，并可机器执行。
Narrative Ontology
先统一 Character/World/Relation/Knowledge/Promise/Resource/Event/Goal/Conflict/Arc/Scene/ReaderPromise 的语义，避免不同模块各自造 schema。
Canon Event Sourcing
Canonical State = immutable events + versioned snapshots；支持回滚、分支、重演、审计、what-if sandbox。
Narrative Transaction
一次生产只在 Commit 时改变正史；生成、推演、修订都是 sandbox。
Knowledge Boundary
每个角色知道什么、不知道什么、从哪里知道、何时知道；用于 POV 与悬念控制。
Promise & Payoff Ledger
读者承诺、伏笔、谜题、爽点债务、感情/成长承诺都有 due window 和 payoff quality。
Narrative Economy
章节必须有净推进；跟踪冲突/信息/资源/关系/地位/目标变化，防止“文字很多但故事不动”。
Commercial Rhythm Model
黄金三章、10章追读、付费点、卷高潮、情绪波形、爽点间距按 Genre Pack 定义，不用统一评分。
Genre Certification
每个 Genre Pack 必须通过对照样本、红队样本、30 章生产测试后才能标记 production-ready。
Context Compiler
把上下文选择视为编译：dependency graph、priority、token budget、freshness、relevance、contradiction、provenance。
Authority Model
区分 deterministic truth / calibrated model evidence / diagnostic model signal / human decision / market truth，禁止总分独裁。
Experiment Plane
模型/prompt/policy/genre/schema/workflow 版本独立；A/B 只修改一个主变量；所有输出可重放。
Artifact Lineage
每个章节能追溯 story snapshot、contract、context、model spec、prompt hash、candidate、review、patch、final、state delta。
Safety & IP Governance
参考语料授权、去重、抽象化、相似度、多源贡献率、secret scan、PII/credentials 禁止进入 artifact。
Cost/Latency Budget
按项目/卷/章/stage/provider 设置预算、限额、降级策略、熔断和缓存。
Failure Injection
随机 kill、API timeout、重复回调、脏数据、并发修改、model refusal、corrupt artifact 必须成为系统测试。

L1 Genre & Narrative Domain

L2 Canonical Narrative State
Canon 是结构化状态，不是一个超长 YAML。Authoring Bible 可以是视图，机器 Canon 由 typed state + event ledger 管理。
状态字段必须标注 immutable / controlled_mutable / dynamic / derived。主角身份等 immutable；关系、财富等 dynamic。
Knowledge Ledger 区分“世界事实”和“角色知道的事实”；POV 只能访问合法知识。
Promise Ledger 管理 planted_at、due_window、status、payoff、reader_importance；避免伏笔无限丢失。
L3 Planning Architecture
Series Vision 只锁定长期方向与核心 Promise；Volume/Arc 决定阶段目标；Chapter/Scene 决定近期可执行任务。
重规划必须产出 PlanDiff：why、affected future nodes、protected promises、new risks；不会悄悄覆盖旧计划。

Contract 是编译产物，不手工散写：Genre + Canon Snapshot + Plan + previous committed output → Chapter/Scene Contract。
TransitionSpec 明确 before / required delta / allowed delta / forbidden delta / postconditions。
Context Compiler 选择最小充分上下文：hard facts、relevant character state、recent timeline、active promises、arc goals、genre policy、style profile。
Context Artifact 必须可哈希、可 diff、可复现；记录为什么包含/排除某条信息。
L5 Intelligence Runtime
Capability roles：planner、writer、reviewer、extractor、classifier、simulator、repairer；不是长期 Agent 身份。
Model Gateway 根据 capability、quality tier、cost、latency、context、structured output 支持情况路由。
Provider 返回统一 ModelCallRecord：model spec、sampling、tokens、cost、latency、request hash、response hash。

9. Genre Constitution：解决“都市写成奇幻”的核心设计
Genre 不再是单个标签，而是“可组合、可版本化、可执行”的 Policy + Guidance。每个 Genre Pack 必须在生成前约束计划，在 Context Compiler 中注入，在生成后进行 deterministic/semantic certification。

9.1 Genre Pack 不是词表
词表只能发现“筑基/灵气”等显性泄漏，无法发现“主角突然凭无法解释的超自然直觉解决商业问题”等语义泄漏。
因此 Genre Validator 必须是双层：deterministic rules + semantic genre classifier。
混合类型必须显式声明，例如 urban_supernatural 允许超自然，但还要限制能力来源、社会公开度、强度曲线与对现实秩序的影响。
Genre Pack 同时携带商业结构：典型开篇承诺、进阶反馈、冲突密度、节奏区间、常见失败模式，而不是只规定“不能写什么”。
9.2 Genre Certification 流程
Genre Pack Draft  → Schema Validation  → Positive Fixtures (应该允许)  → Negative Fixtures (应该禁止)  → Adversarial Semantic Fixtures  → 3-chapter smoke run  → 10-chapter controlled run  → 30-chapter genre drift test  → Human review / error taxonomy  → production_ready

10.2 Context Compiler 决策逻辑
必须：Genre hard policy、当前 Canon snapshot、contract、上一章结尾、涉及人物 immutable/dynamic state、时间线。
相关：active promises、当前 Arc goals、同地点/同人物最近事件、关系变化、知识边界。

11.1 事务语义
关键不变量

12.1 Revision Policy
Revision 不能“随便重写整章”，必须由 violation/evidence 生成 RepairSpec。
RepairSpec 包含 target spans、goal、protected facts、protected good spans、max edit distance、forbidden changes。
同一硬错误最多自动修复 N 次，之后 HUMAN/BLOCK，防止 LLM 修复循环。
任何修订完成后重新执行 Q0–Q3；不能只让同一个 Reviewer 说“修好了”。

23. 最终结论：ANovel V2 应该成为什么
V2 的技术核心不是“写得更聪明”，而是“让创造力只能在合法、连续、可追踪的叙事状态空间中运行”。
V1 已经证明，单纯增加规划器、Reviewer、商业评分、Reader Simulator、Schema 或更强模型，并不会自动得到稳定的商业长篇。真正的瓶颈是：类型边界是否可执行、事实真值是否唯一、规划是否可适应、上下文是否可复现、每章是否是合法状态转换、失败是否能阻断、修订是否不破坏其他事实、长跑是否能恢复、AI 评分是否与人类和市场对齐。
因此 V2 的“创新”不应该表现为更多智能体，而应该表现为更强的 Narrative Kernel。只要 L0–L7 足够稳，GPT、Claude、DeepSeek、Kimi 或后续模型只是可替换的执行能力；如果内核不稳，再强模型也只能降低错误概率，不能给百万字生产提供工程保证。
正式启动裁决
建议立即把本规范设为 V2 Architecture Baseline 1.0。下一份文档不应继续写宏观愿景，而应进入《ANovel V2 Narrative Domain & Canonical State Specification v0.1》，把 Narrative Ontology、GenrePack、CanonEvent、CanonSnapshot、ChangeSet、Promise/Knowledge/Timeline ledger 的字段与不变量正式定下来。
