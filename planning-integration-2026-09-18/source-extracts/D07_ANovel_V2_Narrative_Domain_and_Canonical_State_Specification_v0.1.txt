1. 设计目标
Canonical Narrative State 是 V2 的事实真值层。LLM 可以忘记，Canon 不允许忘记；草稿可以被废弃，Canon 不允许被废稿污染。状态层必须支持长期演化、审计、回滚、派生视图和 Genre Extension。

4. Canon 不等于一个大 JSON
CanonEvent Log  (append-only evidence)        ↓ projectorsCanonical Snapshot (chapter N / scene N)        ↓ selectorsContext Views / Ledgers / Derived Metrics
建议 Event + Snapshot 混合模型：事件保留“发生了什么和为什么”，快照用于高效读取；派生指标由 projector 重建。这样既可审计又可服务生成。
5. Narrative Transaction
State N + Contract + Accepted Exact Body SHA + Extracted Candidate Delta        ↓Deterministic / Semantic Validation        ↓ChangeSet        ↓Commit Permit        ↓ atomicAppend CanonEvents + Update Snapshot + Receipt        ↓State N+1
任何 Draft、Reviewer 输出、Reference Evidence、LLM 抽取结果都只能提出 CandidateDelta；它们没有直接写 Canon 的权限。
6. Knowledge Boundary
长篇悬念与阴谋最常被模型破坏的原因之一，是角色突然知道不该知道的信息。V2 必须把 CharacterKnowledge 作为一等状态，区分事实 Truth 与角色 Belief。

8. Genre Extension
Core Domain 保持稳定；Company/Equity、Realm/Technique、Pet/Evolution 等放入 Genre Extension。扩展必须声明 invariant、event type、projector、context selector 和 certification tests。

10. Retcon 与回溯修改
长篇必然会重写旧章。V2 不能把 Canon 设计成只能向前。Retcon workflow 应创建新 revision lineage，计算受影响的后续事件/Contract/Knowledge/Promise，并在重新认证后才替换 active lineage；禁止直接修改历史快照。
11. Provenance
每个 CanonEvent 必须指向 accepted_body_hash、source_span 或结构化证据。
每个 Snapshot 指向 event cursor / previous snapshot hash / Genre & Story versions。
每个 Chapter Contract 指向 previous accepted state hash，而不是 placeholder。
任何人工修改也必须记录 actor、reason、timestamp、approval。
12. DoD
Canon v0.1 的完成不是 Schema 写完，而是能在一个全新都市项目和一个全新玄幻项目中完成 10→30 章合法事务提交；随机废弃候选、重写章节和进程中断均不会污染或重复提交状态。
