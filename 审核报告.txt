# 二、P0 到底证明了什么

必须把这一点说清楚。

当前：

```text
src/anovel/
└── __init__.py
```

P0 并没有实现小说业务内核。

这是**正确的**，因为 P0 本来的职责就是：

```text
Repository
Runtime
Dependency locking
CI
PostgreSQL environment
Architecture fitness
Governance
Evidence
Security boundary
Execution protocol
```

因此 P0 的完成不能解释为：

> ANovelOS 的小说架构已经通过运行验证。

正确解释应该是：

> **ANovelOS 已建立一个可以在不容易失控、不容易伪造验证、不容易跨越架构边界的环境里开始实现小说业务系统。**

所以：

```text
ENGINEERING FOUNDATION = VERIFIED

PRODUCT ARCHITECTURE =
DESIGNED / NOT YET RUNTIME VERIFIED
```

这个区别必须一直保持到 P8/P9。

# 四、最优秀的几个设计

## 4.1 Canon 和 Context 被正确分开

这是整个架构最重要的决策之一。

当前规范明确：

```text
Canon ≠ Summary
Canon ≠ RAG
Canon ≠ Prompt Memory
Canon ≠ Model Memory
Canon ≠ Plan
Canon ≠ Draft
```

只有：

```text
CanonCommitService
```

可以推进权威叙事状态。

这比很多 AI 写作系统常见的：

```text
memory.json
summary.md
vector db
prompt state
```

共同充当“事实来源”要安全得多。

Novelcrafter 的 Codex 等成熟产品也强调集中管理人物、地点、设定等故事知识；但 ANovelOS 进一步区分了**知识展示/检索层与权威提交层**。

这个方向应该坚决保留。

---

# 五、事实、认知与叙事信息的分离非常正确

当前模型不是简单：

```text
Fact
```

而是区分：

```text
World Fact
Character Belief
Character Knowledge
Reader Revealed Information
Author Plan
```

这是非常关键的设计。

例如：

```text
甲认为乙已经死了
```

不能等价于：

```text
乙已经死了
```

同样：

```text
作者计划第 80 章让乙死亡
```

不能进入当前 Canon。

这直接对应长篇 LLM 最容易出现的问题。

2026 年 ConStory-Bench 对长篇生成做了专门研究，发现长篇模型错误尤其集中在**事实一致性与时间一致性**，并细分出 5 类、19 个子类型。

因此：

```text
Character Knowledge
Timeline
Event
Promise
NarrativeDelta
```

不是为了“架构漂亮”。

它们是直接对应真实长篇失败模式的基础设施。

这是正确投入。

---

# 六、NarrativeDelta 是整个系统的关键设计之一

当前设计不是：

```text
模型生成一章
→ 用模型总结一下发生了什么
→ 更新 Story Bible
```

而是要求：

```text
Candidate Text
        ↓
NarrativeDelta
        ↓
Typed operations
        ↓
Preconditions
        ↓
Evidence location
        ↓
Reducer
        ↓
Commit
```

这使：

```text
“小说文本”
```

和：

```text
“小说世界状态变化”
```

第一次真正分开。

例如：

```text
SET_FACT
CHANGE_RELATIONSHIP
KNOWLEDGE_CHANGE
EVENT_OCCURRED
PROMISE_CREATED
PROMISE_RESOLVED
UNKNOWN
NO_CHANGE
```

这对百万字级系统非常重要。

我认为 **V2-008 是未来整个系统的一个真正架构支点**。

必须避免把它实现成：

```python
dict[str, Any]
```

或者任意 JSON。

否则整个设计会退化回：

> 让 Prompt 自己负责语义正确性。

# 七、Genre 架构目前方向正确，而且吸取了 V1 最重要的教训

当前设计有一个非常好的分离：

```text
Genre World Mechanics
≠
Narrative Strategy
≠
Chapter Constraint
```

例如：

```text
urban.business.realistic
```

意味着世界机制是现实世界。

但不意味着：

```text
必须豪门
必须打脸
必须股票
必须重生
```

同样：

```text
fantasy.eastern.progression
```

也不意味着：

```text
必须退婚
必须宗门大会
必须拍卖会
```

这正好避免 V1 的核心失败：

> 都市被自动写成玄幻。

当前：

```text
Pack ID
version
hash
```

被冻结，而策略检索失败时：

```text
不得替换 Pack
不得选择“最接近的 Genre”
```

这是正确的。

# 八、Context Compiler 的设计方向也非常好

这里我认为 ANovelOS 已经修正了很多 RAG 系统最常见的误区。

当前架构不是：

```text
embedding
→ top-k
→ prompt
```

而是：

```text
Required Context
        ↓
Optional Context
        ↓
Retrieval
        ↓
Budget Allocation
```

其中：

```text
低相似度但必须知道的事实
```

不能因为 top-k 低而被裁掉。

如果 required context 本身超预算：

```text
FAIL / explicit diagnosis
```

而不是：

```text
silent truncation
```

这是非常重要的。

SCORE 的研究也支持动态状态追踪、分层摘要以及时间对齐的混合检索能够改善长篇一致性。

但是 SCORE 报告的：

```text
+23.6% coherence
89.7% emotional consistency
-41.8% hallucination
```

不能直接变成：

```text
ANovelOS 使用 Temporal RAG
= 质量提升 40%
```

而当前 ANovelOS 的正式规划已经明确禁止这种外推。

这是成熟的处理。

# 九、当前架构没有掉进“多 Agent 崇拜”

这是一个非常好的决策。

历史资料中曾有：

```text
Multi-Agent
19 Checkers
Draft A/B/C
Temporal RAG
Emotion checker
PPL
Agent debate
```

同时进入路线的倾向。

现在已经明显收敛为：

```text
能力
→ Contract
→ Service
→ Evidence
```

而不是：

```text
角色名字越多
= 系统越高级
```

这非常正确。

当前公共项目 InkOS 2.0 已经采用统一 agent harness，并让 Studio、TUI、CLI 共用同一个执行内核，而且明确强调“真正完成”依据工具结果和落盘结果，而不是模型口头宣布完成。

这与 ANovelOS：

```text
统一 Workflow
模型不能自己声明 ACCEPTED
```

的方向高度一致。

但 ANovelOS 更应该保持自己的优势：

> Agent 只是执行者，不能成为权威状态所有者。

# 十、长篇路线 3 → 10 → 30 → 100 → 300+ 是正确的

这是另外一个很好的架构决策。

当前不是一上来就：


```text

↓
10 chapter
↓
30 chapter
```

- late defect detection
- continuity accumulation
- flat revision

这恰好说明：

> ANovelOS 提前建立 Canon、章节状态、局部修复和分段认证是有必要的。

# 十六、架构层发现的最重要未来缺口：Durable Workflow 决策还没有正式冻结

当前架构反复强调：

```text
Durable Workflow
Checkpoint
Retry
Resume
Idempotency
Cancel
Late response
UNKNOWN
```

这是正确的。

但当前 `decision-register.yaml` 中：

```text
ADR-001 ~ ADR-016
```

已经没有一项独立解决：

```text
Durable Workflow Runtime / Persistence Semantics
```

历史架构资料曾明确提出类似：

```text
Durable Workflow Port
```

并提出：

> 使用成熟 durable execution 思路，而不是重新发明恢复语义。

现在正式 backlog 中：

```text
V2-020 Single Chapter Workflow
V2-027 Workflow retry and checkpoint
```

会实施这些能力。

但在那之前必须明确：

```text
Workflow state 放哪里
Checkpoint 是什么
Replay 如何工作
LLM side effect 如何隔离
Retry identity 如何定义
Cancellation 如何 fencing
Code upgrade 如何处理旧 workflow
Human wait 如何恢复
```

Temporal 之类的 durable execution 系统，本质就是通过持久 Event History 和 replay 恢复长时间运行流程；其官方文档还明确要求将 API/LLM/DB 等非确定性 I/O 放在 Workflow replay 路径之外。

LangGraph 当前也明确区分：

```text
Checkpointer
vs
Store
```

分别承担 workflow/thread 状态和长期数据。

ANovelOS **不一定要采用 Temporal 或 LangGraph**。

甚至首期很可能：

```text
PostgreSQL-backed explicit state machine
```

就足够。

关键不是选什么框架。

关键是：

> **必须在 V2-020/V2-027 之前冻结 durable execution semantics。**

```text
再修治理工具
↓
业务迟迟不开始
```

因此我建议从 P1 开始采用一个原则：

> **除非真实失败证明现有治理不足，否则不新增治理机制。**

治理应该开始进入“稳定平台期”。

接下来项目时间应该明显转向：

```text
Narrative
Canon
Genre
Planning
Context
Real generation
Reading
```

# 二十一、P1 的最大技术风险反而是“过度建模”

V2-005～008 很容易做成一个巨大的：

```text
Universal Story Ontology
```

这是不必要的。

P1 应严格实现：

```text
minimum sufficient narrative model
```

只解决：

```text
Identity
Alias
Character
Relationship
Knowledge
Belief
Event
Timeline
Promise
NarrativeDelta
```

不要现在加入：

```text
emotion graph
social graph engine
motivation ontology
personality psychology system
dramatic tension taxonomy
30种角色属性
100种事件类型
```

这些应等真实章节暴露缺口。

正确原则：

> **Domain model should be driven by invariants, not by imagination.**

---

# 二十二、P2 也要防止“Event Sourcing Everything”

当前：

```text
Canon events
projection
receipt
rebuild
```

方向正确。

但必须保持边界。

应该 Event Source 的是：

```text
accepted canonical state changes
```

不应该把所有东西都 event-source：

```text
retrieval hit
token count
temporary diagnosis
UI click
model thought
cache entry
```

否则 P2 会迅速膨胀。

建议坚持：

```text
Authoritative history → durable
Derived observations → rebuildable
Diagnostics → evidence store
Cache → disposable
```

# 二十三、架构当前最大的“能力不对称”是：非常擅长防错，但还没有证明“会写得好看”

这是整个项目今后必须警惕的地方。

当前系统非常善于避免：

```text
人物突然改名
死人复活
知识穿帮
题材污染
Timeline 冲突
状态漂移
重复提交
```

这解决的是：

> **不要写错。**

但商业小说还要求：

```text
人物欲望
选择
代价
悬念
兑现
惊喜
节奏
声音
情绪
新鲜感
继续阅读欲
```

也就是：

> **为什么读者愿意继续看。**

当前规划已经意识到这个问题，因此没有把 Q0–Q3 当文学质量分。

这是正确的。

但一定要执行现在已经写进计划的一件事：

### P5/P6 一旦可以生成真实候选正文，就开始极小规模真人读稿

不要等到 P8 才第一次有人读。

可以是：

```text
2–3 chapters
```

不作为正式 Gate。

只作为：

```text
PRODUCT LEARNING SIGNAL
```

目的不是证明成功。

而是尽早发现：

```text
技术上完美
但小说非常无聊
```

这种问题。

# 二十四、与当前外部优秀项目相比

当前公开的 InkOS 已经进入统一 Harness、Studio/TUI/CLI 共用执行核心，并有：

```text
plan
→ compose
→ write
→ review
→ commit
```

以及状态投影和真实落盘结果作为完成依据。

NousResearch autonovel 已经跑出了接近 8 万词作品，并实现 foundation、draft、review、revision、plateau detection 等生产链。

所以如果比较：

| 维度 | ANovelOS 当前状态 | 审核判断 |
|---|---|---|
| Canon 权威模型 | 设计非常强 | 优势 |
| Fact / Knowledge / Belief 分离 | 很强 | 优势 |
| Typed NarrativeDelta | 很强 | 优势 |
| Genre 防污染 | 很强 | 优势 |
| Commit/Permit 安全 | 很强 | 优势 |
| Evidence / reproducibility | 很强 | 优势 |
| Context 设计 | 很强 | 优势 |
| Durable semantics | 方向强，决策待补 | 需补 |
| 实际 Writer | 未实现 | 明显落后 |
| 实际多章作品 | 未实现 | 明显落后 |
| 人类阅读证据 | 未产生 | 未验证 |
| Product Workbench | 延迟 | 有意落后 |
| Reference-learning | P10 | 延迟验证 |
| 真实市场数据 | P13 | 未验证 |

因此目前不能说：

> ANovelOS 已经是最强的 AI 小说系统。

但可以说：

> **从基础架构设计质量来看，它已经具备发展成非常强长篇生产系统的骨架；现在最大的差距已经不是架构想法，而是把这些设计变成真实小说生产结果。**
