## 1. 结论

**报告一更适合用作当前规划的评审意见，但需要纠正 PA-01 的推断和部分过强赞誉。报告二适合用作风险问题清单，不能用作有可信概率、工期和成本预测的可行性报告。**

## 3. 对报告一的评估

### 3.1 对主体架构的肯定基本有文档依据

报告一对模块化单体、唯一 Canon 写入口、候选/计划/工作流与事实分离、双 Anchor、角色认知边界、Context 编译、UNKNOWN 费用、有限修复、真人/基线对照及后期继续投入决定的描述，与现行规范基本一致。它准确注意到 P6 可选读稿和根目录清理，版本匹配也比此前报告好。

但以下表述必须收窄：

| 表述类型 | 更严谨的判断 |
|---|---|
| “Overlay 已解决难题”“系统可以正确表达”“所以不会发生某类错误” | 已建立处理这些问题的设计要求；正确性仍待实现和样本验证，16 个 ADR 仍为 REQUIRED |
| “Gateway 因而不会重复收费”式推断 | 设计要求识别 UNKNOWN 和记录费用；05 第 3 节明确不能保证远端未执行或绝不重复收费。记录责任不等于消除责任 |
| “认证体系非常完整” | 覆盖维度较完整，但运行协议、阈值、数据结构与产物仍待任务内细化，尚无实际认证 |
| “优于普通写作项目”“外部经验吸收充分” | 可作审阅者意见，未提供同条件比较。外部登记仍含 PLANNED、HISTORICAL_UNVERIFIED，不能当源码审计或效果验证 |
| “AI 工程治理已形成真正开发约束” | 本地校验能约束声明；真实 CI、合并规则与数据库权限尚未接入，不是已经运行的完整约束体系 |
| 核心流程把 Repair 串在每次提交前 | Repair 应为检查失败后的有条件分支；现行架构图保留通过检查直接进入 Permit 的路径，不要求合格章节也修复 |
| “APPROVED” | 是报告作者意见，不自动成为机器阶段状态、用户授权或工程验收 |

这些修正不会否定总体设计方向，但能避免“规范写了，所以运行不会错”的推理跳跃。

### 3.2 PA-01：部分成立，不能定性为空任务验收绕过

报告指出两项真实事实：P13/P14 的“进入前补充任务”位于 `exit_criteria`；M11/M12 的最低任务集合为空。它没有充分检查现有代码：

- `phase-gates.yaml:260/272` 已有 `task_refinement: DEFERRED_UNPLANNED`，不是尚缺这一字段。
- `validate_plan.py:147` 只允许阶段 NOT_VERIFIED/VERIFIED，阶段 IN_PROGRESS 当前不是合法状态。
- `validate_plan.py:153` 拒绝空任务阶段 VERIFIED。
- `validate_plan.py:256` 拒绝空 required_tasks 的里程碑 VERIFIED。
- `governance_checks.py:40–41` 还要求里程碑所属阶段已 VERIFIED。
- 冻结检查要求首批 60 个任务身份/阶段不变；目前不能悄悄增加或搬移任务来“填空”。

临时探针以已通过的合成 P0 完成链为正例，仅修改一个条件，观察如下：

| 单点变更 | 实际行为 |
|---|---|
| 合格 P0，P13/P14 维持延期 | 接受 |
| P13 或 P14 改 IN_PROGRESS | 拒绝，PHASE_STATUS |
| P13 或 P14 空任务改 VERIFIED | 拒绝，明确含 unrefined future phase |
| M11 或 M12 空任务改 VERIFIED | 拒绝，明确含 missing scope/evidence |
| P13 空任务、NOT_VERIFIED，只将 task_refinement 改 READY | 接受 |
| 合格且 VERIFIED 的 P0，只将 task_refinement 改 DEFERRED_UNPLANNED | 接受 |

这些探针没有构造完整的 P12 完成链，部分拒绝还伴随前序阶段或证据缺失错误。空任务验收防线的判断同时依据代码中的显式非空条件及对应错误；不能将这些观察泛化为“未来所有阶段进入流程均已正确实现”。

**真实可复现的缺口是 refinement 元数据未参与一致性校验。** 它可以与任务集合/阶段状态矛盾；既有空任务和证据检查仍然有效。`G-P12` 通过不能据此自动推导“当前系统已允许执行 P13”：当前没有阶段进入 API 或合法的阶段 IN_PROGRESS 状态，P13 也没有可启动任务。

建议将 PA-01 改写为“未来阶段准入表述和细化元数据一致性不够明确”。可在治理接入时补枚举、任务集合/状态一致性及正反例；明确前序 Gate 通过只是必要条件。不必新增一套可手改的 `may_enter` 真相源，也不必现在设计 P13/P14 全部功能。

未来真正增加后续任务时，仍须同步 backlog、验收、ADR、里程碑最低集合与冻结校验；空最低集合确实不能永久沿用。此项值得处理，但**不构成当前 P0 阻塞，也没有复现空任务关闭绕过**。

### 3.3 PA-02：任务输出栏确实可更清晰，但认证证据设计并未缺失

V2-033/034/035/040 的 `artifacts` 主要列 runner 和 test，这是报告观察正确的部分。已有覆盖也很明确：

- 06 第 2～3 节要求真实运行证据、完整分母、正文与收据、恢复、原始读稿和成本。
- `CHAPTER_CERTIFICATION_RECORD.yaml` 已含 protocol/hash、chapter_receipts、all_attempt_refs、cost_ledger_ref、human_intervention_ref、continuation_decision_ref 等。
- 06 第 9 节和 ADR-013 要求在首次认证前冻结协议。
- 09 第 1 节要求 PLANNED 任务开始前补齐实际产物路径与验收。

因此这是**从规范到具体任务输出的细化缺口**。建议在 V2-033 开始、首次认证前明确运行包结构、输出路径、版本/正文/收据绑定和内容校验。当前通用治理 Schema 并不懂小说认证的业务含义，模板字段存在也不等于已实现运行结果校验。

无需现在新建报告列举的六个独立实体或服务。V2-037～039 是检查器，不应机械要求每个任务都单独产生完整认证包。P0 不受影响。

### 3.4 PA-03：执行拆分建议合理，处理时点应靠近实际消费者

V2-040 覆盖都市与玄幻各 30 章，以及恢复、持续性、读稿、人工、成本、基线和继续投入。复杂度确实值得管理，但现有目标、验收与下游消费已经写明，不能称为没有验收设计。

可复用 V2-017 的做法，在 **V2-040 转 IN_PROGRESS 前**准备内部执行包：分别记录两个题材运行、故障证据、叙事分析、读稿、全成本、继续投入和最终聚合。每个子结果绑定同一适用版本，允许分开诊断失败，但子项完成不等于总任务完成。

报告提出“G-P8 前必须有执行包”偏早，可在 P8 后期准备，却不需要新增一个 G-P8 硬门禁。保留一个任务 ID 合理。

### 3.5 PA-04：有维护便利价值，尚未证明发生上下文失效

实际静态关联数量：V2-002 有 20 个 finding、5 个现行规范、6 个参考和 12 个场景；V2-040 有 14 个 finding、2 个规范、4 个参考、5 个场景和 1 个 ADR。全表单任务 ADR 最大为 3 个。

这些数字证明引用量较大，不证明模型已超上下文、遗漏约束或开发质量下降。现行规则本来就要求按当前任务读取相关资料，并非每次递归读取整个 archive。

可按需要试用由机器源生成的任务索引，包含原始字段、相关义务、来源版本和跳转链接；不以生成摘要替代规范，不静默删减 finding，也不另立 SSOT。无需为了此建议提前生成 60 份新文档或新增 P0 准入门槛。

## 4. 对报告二的评估

### 4.1 风险方向应保留

以下问题真实且值得持续测量：语义检查的误报漏报、模型与评审器可能共享盲点、修复循环的全成本、必要人工贡献、长篇一致性、读者实际喜好、发布条件与收益不确定性。工程门禁通过不会自动证明文学质量。

报告二的价值是提醒这些未验证假设；不足是把风险问题写成了没有来源的定量结论，并将已有的验证路线说成“没有安排”。

### 4.2 概率、工期与成本不能作为项目事实

| 报告数字/推论 | 复核判断 |
|---|---|
| 达到 M7 概率约 35%、商业成功约 9% | 未给成功定义、时限、参考样本、概率模型或校准。不能用于决定做/不做，也不能用另一个主观数字替换 |
| Canon 瓶颈概率 40%–50%、单人规模失控概率 60%–70% | 没有基准负载、实测或样本依据，最多是不确定风险的文字标签 |
| 单人 18–28 个月；另处 P0–P9 8–12 个月 | 可能针对不同范围，但报告未说明，也没有任务估算、可用时间、吞吐或关键路径推导；属于假设，不能成为启动条件 |
| 每本 $500–1000；另处 $500–3000 | 书的篇幅、接受章节数、模型、token、重试和人工口径不统一，无法比较 |
| 每章 10 次调用 + 5 次修复 + 3 次检查，所以 $5–10 | 次数本身推不出金额；还缺每次输入/输出规模、模型计价、缓存、失败、工具和修复条件 |
| 300 章总计 $1500–3000 | 乘法正确，但只是“每章确为 $5–10”条件下的结果；不能反过来证明每章成本 |
| 30% 章节需人工，因此 300 章需要 90 小时 | 只能推出 90 个章节涉及人工；90 小时还隐含每章恰好 1 小时，报告未给依据 |
| 8,746 行规划、7 模块、60 任务证明规模超出个人能力 | 行数/模块的统计范围未说明；规模提示不等于所需人月或失败概率，更不证明固定人数要求 |

较可复算的口径应为：总模型费按各次调用的实际模型、token 与计价记录求和；已确认费用与 UNKNOWN 待核责任分开列示；再记录基础设施、人工分钟数、所有失败/中止，以及接受章节数和实际字数。人工成本要注明采用的计价假设，不能只数“有人工的章节”。

本轮未查价、未做实际成本模型或收益预测，因此不提供替代美元估计；同样不声称项目便宜、昂贵或有某个商业成功概率。

### 4.3 “质量检测不可能三角”不是被建立的技术结论

报告没有定义三个相互冲突的性质、成立条件或不可兼得证明。模型评估可能有相关错误和偏差，但“用模型评估模型输出”本身不能推出必然不可行。

相关原始研究确实研究了位置、冗长和自我偏好等偏差，也研究模型判别与人工偏好的关系；这支持谨慎校准，并不构成“不可能三角”。该研究的聊天基准结论不能直接外推到中文长篇、题材污染或本项目成功率。[Zheng 等：Judging LLM-as-a-Judge](https://arxiv.org/abs/2306.05685)

本项目已有确定性检查、语义证据/UNKNOWN、人工裁决、开发与 holdout 分离，以及真人对照要求。真实尚待回答的是：逐类错误的漏报/误报、遗漏覆盖、已知合法语境的拒绝率、人工分钟数和每接受章节全成本。应将其作为 V2-021～026 与 P8/P9 的实验问题，而不是凭“不可能”停止或凭“有多层检查”宣布解决。

### 4.4 Canon 瓶颈提醒合理，20–30 秒推断没有依据

角色/事件条数不足以推出延迟，报告也将 Canon 写入、查询、Context 编译和模型时间混在一起。当前设计采用 project/branch 作用域、短事务，模型调用和长评估在事务外；唯一逻辑写入口不自动等于所有项目排队执行一个长期事务。

正确结论是“性能未测”。未来应分开量测事务/锁等待、查询与序列化、上下文选择和 Provider 时间，用实际 Schema、索引、数据分布、并发和硬件记录结果。PostgreSQL 官方提供 `EXPLAIN ANALYZE` 的实际行数/耗时及 `BUFFERS` 统计用于分析，但这些方法本身并不保证本项目性能。[PostgreSQL 官方 EXPLAIN 文档](https://www.postgresql.org/docs/18/using-explain.html)

不应据此提前引入图数据库、缓存集群或微服务，也不能反向声称 PostgreSQL 必然足够快。文档版本仅用于引用诊断方法，不替项目选择数据库版本。

### 4.5 商业目标与首期形态被部分混淆

当前首期明确服务内部单一操作者，后续以真实读者和市场结果验证。它不是尚未决定客户和定价的 SaaS 项目，因此“没有订阅定价/外部客户”不能直接作为 P0 缺陷。

作品是否吸引读者、全成本能否接受、可采用的发布渠道及收入是否覆盖投入仍未知。报告提出平台政策问题可以保留，但没有给原文、版本、适用主体或条件，不能推断起点允许或禁止某类作品。本轮不作平台资格或法律判断。

“商业成功仅 9%，所以赚钱不推荐；学习值得，所以推荐”建立在没有依据的概率和未确认的个人偏好上，不是本项目决策依据。项目仍应围绕中文网文阅读竞争力评估；学习收益可以记录，但不能替代用户的产品目标。

### 4.6 启动条件和第一个月计划需要纠偏

明确执行角色、真实环境、停止条件和预算是有用要求。固定 1–2 人全职、固定 28 天、先承诺 18–28 个月，则没有必要作为 P0 门槛。

“远程 CI 配置已完成”不应同时成为 P0 的前置完成条件与 V2-004 的待交付成果。可先核实权限和可用环境；实际配置、负例阻断与当前提交证据在 P0 完成。报告第 1 周的“数据库 Schema + SQLAlchemy 模型”也必须限定义务：若是连接/隔离测试夹具，符合 P0；若是 Narrative/Canon 业务表和迁移，则提前进入了 P1/P2。

P0 的架构导入/能力边界测试不等于 P2 的数据库业务写权限和并发事务验证。应沿用已有任务阶段，不用周计划暗中前移。

## 5. 建议如何使用这两份报告

| 意见 | 建议处置 | 最晚适用时点 |
|---|---|---|
| 保持总体架构、开始有边界的工程验证 | 保留；当前资料足够开工，不承诺后续业务成功 | P0 |
| PA-01 细化元数据与准入文字 | 部分采纳，收窄为真实观察，不标空任务关闭漏洞 | 治理接入可顺带处理；未来阶段入口消费/扩展前落实 |
| PA-02 认证运行包 | 采纳任务输出细化，复用已有协议与模板 | V2-033 开始、首次认证前；30 章输出在 V2-040 开始前 |
| PA-03 V2-040 内部执行包 | 保留建议，不改任务 ID、不新增 G-P8 门槛 | V2-040 转 IN_PROGRESS 前 |
| PA-04 任务上下文索引 | 按需试用生成视图，先看实际收益 | 执行中需要时 |
