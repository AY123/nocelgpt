## 🎯 Stage 3 任务列表

### Task 3.1: Validator 去硬编码 (1.5-2h)

**问题**:
```python
# 当前 check_candidate() 中的硬编码
location_keywords = {
    'loc_city_square': ['广场', '市中心', '城市广场'],
    'loc_mysterious_ruins': ['遗迹', '废墟', '古迹'],
}
```

**目标**:
- 从契约或配置文件加载地点关键词
- 支持用户自定义检查规则
- 可配置的检查策略

**实现方案**:
1. 创建 `contract_validation_config.yaml`
2. 定义可扩展的检查规则格式
3. 重构 check_candidate 使用配置

**验收标准**:
- ✅ 无硬编码地点关键词
- ✅ 支持从配置加载规则
- ✅ 向后兼容（无配置时使用默认）

---

### Task 3.2: Source Hash 过期检测 (1-1.5h)

**问题**:
- 契约引用 outline，但 outline 变化后契约未更新
- 无法检测契约是否过期

**目标**:
- 检测契约的 sources.content_hash 是否过期
- 在 precheck 时警告过期契约
- 提供"重新生成"建议

**实现方案**:
1. 在 precheck 时计算当前 source hash
2. 对比 contract.sources.content_hash
3. 不匹配时发出警告（advisory，不 gate）

**验收标准**:
- ✅ 检测过期契约
- ✅ 警告但不 gate（ADR-003）
- ✅ 提供重新生成的路径

---

### Task 3.3: 审批审计与版本管理 (1-1.5h)

**问题**:
- 契约的 approved 字段是布尔值，无审批历史
- 无法追踪"谁批准的"、"何时批准的"
- 契约修改后无版本管理

**目标**:
- 记录审批历史（who, when, why）
- 支持契约版本演进（v1.0 → v1.1 → v2.0）
- 审计追踪

**实现方案**:
1. 扩展 contract schema 添加 approval_history
2. 记录每次审批的元数据
3. 版本号自动递增机制

**验收标准**:
- ✅ 审批历史可追溯
- ✅ 契约版本可管理
- ✅ 向后兼容现有契约

---

### Task 3.4: 真实章节金样评估 (0.5-1h)

**问题**:
- 所有测试都是 mock 数据
- 未在真实章节上验证

**目标**:
- 选取 3-5 个真实章节
- 为它们创建契约
- 运行完整的 Contract Gate 流程
- 评估结果质量

**实现方案**:
1. 从现有项目选取代表性章节
2. 创建高质量契约
3. 运行 run_serial --enable-contract-gate
4. 分析结果，记录发现的问题

**验收标准**:
- ✅ 至少 3 个真实章节测试
- ✅ 记录实际效果（pass rate, 修订率）
- ✅ 发现并修复实际问题
