## 1. 执行摘要

ANovel 当前的核心问题，不是“系统是否存在”，而是“系统写出来的中文商业网文，是否已经被真实证明足够好看、足够能卖、足够能长连载”。

从当前仓库与前两轮审核结论综合判断，项目已经具备较强的工程骨架与事实治理能力，但仍缺少足够的真实作品证据链来证明：

- 黄金三章是否足够抓人；
- 前十章是否能维持追读；
- 前三十章是否兑现商业承诺；
- 自动修订是否真的提升人工盲评结果；
- 模拟读者与商业评分是否已被真实平台数据校准；
- 百章到百万字的连续生产是否稳定。[报告判断]

因此，后续推进必须从“继续扩建工程结构”转向“证明作品结果”。

**总主线**：

项目事实恢复 → 中文正文稳定 → 30 章真实产品基线 → 人工金样集与质量校准 → 自动修订净收益验证 → 百章长线规划 → 成稿事实回流 → 可恢复百章生产 → 上架包 → 真实平台反馈 → 百万字生产验证

### 2.2 裁决结论

两份审核报告没有实质路线冲突，差异主要是叙述粒度与阶段排序细节。统一裁决如下：

1. 不再把“新增更多 Agent / Schema / 报表”当作进度；
2. 不再把模拟评分当成真实商业结论；
3. 不再把文档增量当作能力增量；
4. 先证明正文质量，再证明长线稳定，再证明真实商业反馈。

## 3. 当前项目真实状态

### 3.1 已经完成什么

#### [事实]
- 根 `README.md` 仍为 GitLab 默认模板，未真实反映项目状态。
- `ROADMAP.md` 已是较完整的 as-built 账本，记录了已实现与 deferred 内容。

#### [报告判断]
- 标准层、运行时层、事实系统、回放 / 审计、导演控制、发布 / 信号读侧视图等关键链路已经成形。
- 系统已经不是“没有能力”，而是“缺少被真实验证过的小说产品结果”。

### 3.2 半完成什么

#### [报告判断]
- 题材理解、商业定位、读者模拟、自动修订、长弧规划都已具备结构，但尚未被真实校准。
- 30 章、100 章、百万字能力都不是空白，但也没有足够证据证明已达商用水平。

### 3.3 尚未完成或尚未证明什么

#### [报告判断]
- 黄金三章是否真强。
- 前十章是否真能留存。
- 前三十章是否兑现商业承诺。
- 自动修订是否真改善作品。
- 模拟读者是否和真实平台行为对齐。
- 百万字是否会在中后期崩坏。

### 3.4 当前最大瓶颈

#### [报告判断]
不是“少模块”，而是**缺真实结果的证据链**。

### 3.5 当前最强能力

#### [报告判断]
工程约束强、事实链强、可审计性强、可恢复性强。

### 3.6 当前最危险的误判

#### [报告判断]
把“有字段 / 有 Schema / 有 Agent / 有 Reviewer”误认成“已经具备商业小说竞争力”。

### 3.7 下一阶段应从什么转向什么

#### [报告判断]
从**工程完成度导向**转向**作品结果导向**。

具体来说，就是从：
- 增加模块；
- 增加评分维度；
- 增加 Agent；
- 增加报告层；

转向：
- 证明正文质量；
- 证明自动修订收益；
- 证明真实留存与付费信号；
- 证明长篇稳定性。

## 4. 项目核心判断与能力分层

### 4.1 五个层级必须区分

1. **工程能力已经存在**：代码与契约层具备能力。
2. **功能已经真实接线**：模块之间有真实消费链路。
3. **真实模型已经跑通**：不是 deterministic stub，而是真实 LLM / 真实运行路径。
4. **小说质量已经得到人工验证**：经过人工盲评、金样集或真实基线验证。
5. **商业价值已经得到平台数据验证**：真实平台行为、首订、追订、留存等结果验证。

这五层不能混为一谈。

### 4.2 当前状态判断

| 层级 | 当前判断 | 说明 |
|---|---|---|
| 工程能力已经存在 | 基本成立 | 多数核心链路在仓库中已有实现或 seam [报告判断] |
| 功能已经真实接线 | 部分成立 | 一些链路已接线，但长篇/商业/校准闭环仍未完全证明 [报告判断] |
| 真实模型已经跑通 | 部分成立 | 真实 LLM 路径存在，但仍需按最新仓库状态逐项核验 [报告判断] |
| 小说质量已经得到人工验证 | 未证明 | 缺少 30 章 / 100 章 / 金样集级别的真实质量证据 [报告判断] |
| 商业价值已经得到平台数据验证 | 未证明 | 缺少真实平台闭环数据 [报告判断] |

## 7. 修订后的总体路线图

### 7.1 主线顺序

1. 项目事实恢复
2. 中文正文稳定
3. 30 章真实产品基线
4. 人工金样集与质量校准
5. 自动修订净收益验证
6. 百章长线规划
7. 成稿事实回流
8. 可恢复百章生产
9. 上架包
10. 真实平台反馈
11. 百万字生产验证

### 7.2 为什么这样排

- 前四步是在回答“这本书能不能写对、写稳、写得像人写的”；
- 中间三步是在回答“自动修订与长线规划有没有真实收益”；
- 后三步是在回答“能不能规模化、能不能上架、能不能被真实读者验证”。

### 7.3 应删除或降级的路线项

- 继续新增 Reviewer / Persona / Agent 角色；
- 继续建设没有消费者的新 Schema；
- 继续做复杂 UI；
- 继续把模拟评分当成真实商业结果；

## 14. 2026-07 下一阶段战略增补：Corpus Intelligence

> 本节依据 2026-07-25 仓库状态增补。若与本文较早的 30/90/180 天排序冲突，以本节和 `docs/ANOVEL_WEEKLY_EXECUTION_PLAN.md` 的最新审计状态为准。

### 14.1 阶段裁决

当前工程主链已经越过“补基础模块”阶段：30 章真实基线、作品级 100 章 Long-Arc、真实模型消费、事实候选规范化、Scheduler / Resume / Manifest 等能力已经存在。真人评审与真实平台校准暂缓期间，下一阶段不再以扩充 Reviewer、Schema、Prompt 主版本或重复工作流为主，而应将数万本优秀小说储备转化为可审计、可检索、可被生产链真实消费的叙事知识。

下一阶段第一优先级正式定义为：

> **CI-M1：Corpus Intelligence MVP——建立可版本化语料快照、作品叙事画像和 Genesis 证据包，并证明现有 Genesis 真实消费。**

紧随其后的第二优先级为：

> **CI-M2：闭合 W12 的 Mint → Recompute → 下一章 Objective / Prompt / Draft 消费链。**

### 14.2 目标架构

系统按三个平面和一个学习闭环深化：

1. **Knowledge Plane**：语料治理、叙事挖掘、模式聚合、条件统计和检索；
2. **Production Plane**：Genesis、Long-Arc、Chapter Objective、Scene Plan、正文、修订和上架包；
3. **Control Plane**：确定性检查、多模型 Pairwise、选择、原创性、成本、审计和恢复；
4. **Learning Loop**：AI 比较结果、长跑结果与未来真实 ReaderSignal 共同更新版本化策略。

知识层是外部证据，不是项目事实；生产层默认只消费抽象 Evidence Pack，不直接消费参考小说原文；任何策略更新必须发布新版本，不能静默改变运行中的作品。

### 14.3 CI-M1 最小范围

第一版不直接处理数万本，也不先建设复杂 UI。选择一个目标题材建立小规模垂直样本：

- 高表现作品 80 本；
- 普通对照作品 40 本；
- 高开低走或中期失速作品 20 本；
- 合计约 140 本；工程开发先用 10 本 fixture corpus 验证。

MVP 只建设四类产物：

1. `CorpusSnapshot`：固定作品清单、内容 hash、授权边界、去重状态、分析器 / Prompt / Model Policy 版本；
2. `BookNarrativeProfile`：核心幻想、目标读者、卖点、主角缺口与欲望、金手指及限制、首次可见回报、第一卷承诺、30–100 章增长轴和中期风险；
3. `GenesisEvidencePack`：面向一次开书请求聚合统计基线、正向模式、失败模式、原创性约束和 provenance；
4. Genesis 消费证明：Evidence Pack 进入 Outline Bootstrap，引用写入 final outline provenance，并能在受控 A/B 中改变候选。

首版暂不将 Evidence Pack 直接接入 Writer。先证明“知识改变规划”，降低模仿原文和文风污染风险。

### 14.4 语料边界与原创性原则

- 原始语料必须有来源、授权、内容 hash 和版本；
- 生产 Agent 默认不可见真实作品名、作者名、平台外部 ID 和连续原文；
- 正式 Pattern 必须来自多个作品簇，并报告单一来源贡献率；
- 只有优秀样本不足以发现成功差异，必须保留普通和高开低走对照组；
- 检索结果必须多源组合，不允许单本书成为完整模板；
- 原创性检查同时覆盖文字、语义、事件序列、角色功能、关系图和冲突—回报顺序；
- Corpus 不得写入项目 `registry/facts/**`，事实仍只能通过唯一 Mint 入口写入。

### 14.5 AI 优先的质量控制

真人评审暂缓后，AI 证据分三级管理：

- **E1 确定性证据**：长度、重复、红线、实体、时间线、伏笔超期、角色沉寂、相似性，可参与硬约束；
- **E2 多模型比较证据**：匿名 Pairwise、A/B 位置交换、多模型投票和分歧仲裁，可用于候选排序与选择；
- **E3 商业预测证据**：模拟追读、首订、付费、月票和弃书，只能诊断和排序，真实平台数据到来前不得称为商业真值。

W10 已证明开放式自动修订不应默认开启。修订策略保持 `restrict`，后续转为有明确 span、保护事实和角色意图、可回滚并带多维回归检查的 Patch-first 模式。

### 14.6 分期顺序

严格执行以下顺序：

1. `CI-M1A`：Corpus Snapshot 与 10 本 fixture corpus；
2. `CI-M1B`：Book Narrative Profile 的 deterministic / LLM / consensus seam；
3. `CI-M1C`：Genesis Evidence Pack 与 Outline Bootstrap 消费；
4. `CI-M1D`：A/B/C 三臂 Genesis 实验，决定是否扩到约 140 本；
5. `CI-M2`：W12 下一章消费闭环；

7. `CI-M4`：Chapter Function Signature、Promise / Character Arc / Narrative Economy Ledger；

9. `CI-M6`：验证后扩展到数万本，并预留真实 ReaderSignal 校准。

### 14.7 CI-M1 出口标准

只有同时满足以下条件，才能扩大语料规模或把 Evidence 接入正文 Writer：

- 固定 `CorpusSnapshot` 可重放，作品清单和 manifest hash 可复核；
- 每个 `BookNarrativeProfile` 有分析版本、证据、置信度和 Schema 校验；
- `GenesisEvidencePack` 不含连续参考原文或可识别专名；
- Genesis 记录 corpus snapshot、query hash、retrieval policy 和 pattern/profile refs；
- 开关关闭时旧 Genesis 路径保持兼容；
- A/B/C 实验中 Corpus Evidence 组相对当前基线的匿名 Pairwise 胜率高于 60%；
- A/B 交换位置后结论一致率不低于 75%；
- 100 章可持续性不低于基线，原创性风险不高于基线；
- 所有新增 Artifact 均有真实消费者，不出现平行 Schema 或无消费者模块。
