# ANovel 旧基线冻结记录

> 目的：冻结当前 2–3 章的旧版本样本，作为后续正文质量改造、长度收口、角色声音修复与 winner 一致性修复的对照基线。
>
> 说明：本文件只记录冻结边界与后续应补的证据，不替代运行日志、章节正文或评审记录。

## 1. 冻结原则

1. 冻结的是“当前可回放的旧版本样本”，不是最终产品。
2. 冻结时应保留 prompt、run、cost、state、quality 等产物的指针或路径。
3. 冻结样本只用于对比，不作为未来正文质量的目标上限。
4. 若后续实现了更完整的基线记录方式，应保留本文件作为历史对照。
5. 冻结记录应优先链接真实产物，再写人工摘要。

## 1.1 当前仓库里可直接对接的记录形态

仓库中已经存在与冻结记录相近的两个读侧产物：

- `AI-Novel-Runtime/runtime/serialize/run_manifest.py`：用于把一次 serial run 与 draft envelope、chapter-final、成本与 token 使用折叠为 run manifest。
- `AI-Novel-Runtime/runtime/serialize/live_baseline_report.py`：用于把真实多章 live run 折叠为统一审计报告。

这两个产物对应能力矩阵中的两项基础审计能力：

- `run manifest`：单次 serial run 的审计记录；
- `live baseline report`：真实多章基线的统一报告。

这意味着冻结记录不需要重新发明记录格式，而是应与现有 manifest / baseline report 对齐：

- `run_manifest_ref` 应指向一次 run 的导出路径；
- `quality` 应引用章节级评审或报告路径；
- `replay` 应引用可重放输入、产物和运行结果；
- `provenance` 应能追溯到章节正文与对应事实/状态快照。

## 3. 冻结执行清单

按以下顺序补录，避免只写摘要不写证据：

1. 锁定章节范围与章节 ID。
2. 记录对应 prompt 版本与输入条件。
3. 记录 run 入口、开始/结束时间、输出目录。
4. 记录 cost、token、provider、model。
5. 记录 state / facts 快照或引用路径。
6. 记录 quality 评审、问题标签与人工修改。
7. 记录 replay 方法与可复现命令。
8. 记录是否已生成 `run_manifest` / `live_baseline_report`，以及它们的路径。
