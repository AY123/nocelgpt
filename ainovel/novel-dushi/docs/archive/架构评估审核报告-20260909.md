# 《重生之金融帝国》生成系统架构评估审核报告

**审核日期**：2026-09-09  
**审核范围**：大纲生成、事实/事件注册、章节规划、章节生成、连续性质量门禁、生产状态机、成书导出  
**审核对象**：`novel-dushi` 生产数据与 `AI-Novel-Runtime` 执行代码  
**审核结论**：30章生产链当前 P0 不可用；不是所有代码都需要推倒重来，但“可信故事状态 + 连续生成 + 质量决策 + 发布导出”这一核心控制闭环已经失效。

## 一、结论摘要

这次事故不是单个 LLM 输出失误，也不是第一、二章之间缺一段过渡。它是四个层面的系统性故障叠加：

1. **大纲语义不足**：章节目标使用“小敌人”“生存威胁”等模板化标签，没有主角、对手、地点、时间、事件动作和章节出口。
2. **事实与事件没有成为硬约束**：事实库中的主角甚至是“未命名主角”，章节事件只有抽象名称和抽象 summary，无法给生成器提供唯一故事线。
3. **章节生成没有单一前驱状态**：运行时虽然有 `story_state`、character runtime、scene plan、director brief 等投影，但多数是 advisory，缺失时会静默降级；没有“上一章出口必须被下一章消费”的硬条件。
4. **质量状态和导出状态分裂**：章节生产决策明确要求 `revise + hold_for_human_review`，但同一记录又写成 `publish_readiness=ready`；导出器按 draft 存在即可收集，最终将未批准内容拼成成书。

因此，当前系统可以保留 registry、schema、outline-memory、chapter pipeline 和质量模块的骨架，但必须先重建它们之间的可信数据契约、单一状态机和发布边界。继续增加 Prompt、评分器或“再跑一次”不会解决根因。

## 二、直接证据

### 1. 大纲与正文事实不一致

大纲写明世界观是“2013-2023年中国金融市场与互联网创业浪潮”，主角是陈默，配角是周江、苏晴、林志远，见 [OUTLINE-00001.md](/Users/angyang/Documents/xiaoshuo/AINovel/novel-dushi/registry/derived/outline/OUTLINE-00001.md:15)。

但成品第1章使用林远、2009年、盛达咨询、恒泰地产；第2章改成林远泽、星耀传媒、陈浩宇；第3章改成陈峰、2007年、恒远地产；第4章又改成林晓。30章中还出现林昊、林晨、林晚、陈默、林烨、林舟、陆锦川、陈远等多个互不一致的主角。

### 2. 事实库没有提供可执行故事事实

当前主角事实 [CHR-90001.yaml](/Users/angyang/Documents/xiaoshuo/AINovel/novel-dushi/registry/facts/characters/CHR-90001.yaml:1) 的 `name` 是“未命名主角”，没有年龄、地点、身份、关系或当前目标。

第1、2章事件 [EVT-90004.yaml](/Users/angyang/Documents/xiaoshuo/AINovel/novel-dushi/registry/facts/events/EVT-90004.yaml:1) 和 [EVT-90005.yaml](/Users/angyang/Documents/xiaoshuo/AINovel/novel-dushi/registry/facts/events/EVT-90005.yaml:1) 只有抽象章节名、抽象 summary、空 `locations` 和同一个未命名角色。它们没有定义“谁在何时何地做了什么、造成什么不可逆结果”。

### 3. 章节骨架会主动制造抽象目标

`_build_first_30_chapters()` 会把冲突阶梯中的模板标签写入每章目标，例如“阶段boss”“生存威胁”“逼主角用出金手指”，见 [agents.py](/Users/angyang/Documents/xiaoshuo/AINovel/AI-Novel-Runtime/runtime/outline/agents.py:323)。该函数检查的是字段是否存在、节奏是否变化，不检查每章是否拥有具体人物、地点、行动和因果链。

大纲 QA 同样主要检查 golden finger、power tiers、conflict ladder、end_hook 等结构字段，见 [qa.py](/Users/angyang/Documents/xiaoshuo/AINovel/AI-Novel-Runtime/runtime/outline/qa.py:37)。它可以判定“骨架完整”，却不能判定“故事可连续生成”。

### 4. 连续性检查检查错了对象

`check_cross_chapter_continuity()` 主要检查上一章是否缺句号、下一章是否接上半句，见 [text_integrity.py](/Users/angyang/Documents/xiaoshuo/AINovel/AI-Novel-Runtime/runtime/execution/text_integrity.py:193)。它不检查主角身份、日期、地点、组织、人物关系、未完成动作和章末承诺。

运行时确实会加载 `story_state`、actual exit、character runtime、chapter contract 等上下文，见 [loop.py](/Users/angyang/Documents/xiaoshuo/AINovel/AI-Novel-Runtime/runtime/serialize/loop.py:817)，但这些路径大多是可选投影；缺失、低置信度或版本不匹配时会降级为空字符串或咨询性警告，不能阻止下一章生成。

### 5. 质量决策与发布状态发生 split-brain

第2章生产决策是 `action=revise`、`advance_to_next_chapter=false`、`hold_for_human_review=true`，见 [final-TASK-00002.json](/Users/angyang/Documents/xiaoshuo/AINovel/novel-dushi/registry/derived/chapter-final/final-TASK-00002.json:310)。

同一 artifact 的 `final_review.publish_readiness` 却是 `ready`，见同文件第5-26行。RUN-00030 中30章全部呈现“禁止推进 + 等待人工审核 + ready”的矛盾组合。

### 6. 导出器绕过生产门禁

`assemble_book()` 对 `produced` scope 直接遍历 drafts；对于 `published` scope，它只依赖 published log/inventory，不校验 chapter-final 的最终状态是否允许发布，见 [book.py](/Users/angyang/Documents/xiaoshuo/AINovel/AI-Novel-Runtime/runtime/export/book.py:59)。因此失败或待审核章节仍然可以进入用户看到的 txt。

项目另有一个 fail-closed 的 `ReleasePackage`，其 `can_release` 要求 `status=approved`，但普通 book exporter 没有消费这个发布包。结果是“发布包设计正确、实际成书入口绕过发布包”，属于控制面旁路，不是单纯字段命名问题。

### 7. Outline 到 Facts 的导入结果发生漂移

本次 outline import plan 中 `CHR-90001` 原本明确命名为“陈默”，但实际 facts 中同一 ID 变成“未命名主角”。这表明候选、人工审核、导入或后续覆盖之间没有可靠的内容 hash/版本绑定。即使 outline 某处写对了，生产时消费的事实仍可能是另一份内容。

### 8. 生产运行没有启用已有的强契约能力

最终批次 RUN-00030 使用的是 Prompt `6.0.0`。v6 只要求 story state、IR、scene plan、character runtime 和 director brief；明确约束 entry state、上一章实际出口及 chapter contract 的能力位于 v15。也就是说，代码库里虽然出现了更强的设计，但实际30章生产没有使用它；项目缺少“最低生产版本”门禁，属于部署配置和架构治理的共同缺陷。

## 四、架构判断

### 不是“所有模块都废了”

以下部分可以保留并作为重构基础：

- registry 的版本化 artifact 目录和 provenance 机制；
- outline、scene plan、chapter IR、character runtime 的数据结构方向；
- chapter contract 的 entry/exit 概念；
- 运行时的模型适配层、重放和 hash 记录；
- 分离 deterministic gate 与 evaluative review 的总体思想。

### 但生产控制面已经失效

当前系统把“存在一个结构化 artifact”误当成“artifact 具备叙事语义”，把“评分器给出 pass”误当成“事实连续”，把“生成了 draft”误当成“可以导出”。因此，30章生产能力必须判定为不可用，现有 txt 必须作废，不能以局部修订方式交付。

## 五、目标架构

### 1. Canonical Story Bible

在任何章节生成前，必须存在唯一、人工确认的故事圣经，至少包含：

- `protagonist`: 固定姓名、年龄、身份、起点时间、所在城市、核心欲望、缺陷、能力边界；
- `cast`: 每个角色的姓名、角色类型、关系、已知事实、当前目标；
- `world_rules`: 年代、行业、法律/技术边界；
- `locations`: 城市、公司、住所、会所等可引用地点；
- `timeline`: 绝对日期或相对日期锚点；
- `lexicon`: 不得变体的专名、别名和禁用名；
- `open_threads`: 当前未完成任务、承诺、威胁和下一章必须消费的出口。

没有 Bible 或 Bible 未经批准，禁止进入章节生产。

### 2. 具体化的 Chapter Contract

每章不能只有 goal。必须有机器可校验的：

```text
entry_state: 时间、地点、POV、在场角色、上一章出口
objective: 本章要完成的具体动作
conflict: 具体对手和阻力
beats: 3-6 个有因果关系的场景动作
irreversible_change: 本章结束后不可回退的状态变化
exit_state: 结束地点、在场角色、未完成动作
hook_promise: 下一章必须承接的明确问题
```

“小敌人”“生存威胁”“阶段翻身”等只能作为标签，不能作为唯一内容。

### 3. 严格串行状态机

章节 N 只有在章节 N-1 取得 `allowed_to_advance=true` 且存在签名的 `exit_state` 后才能生成。章节 N 的 contract 必须引用 N-1 的 artifact hash 和出口 hash。任何缺失、冲突或低置信度字段都应阻塞，而不是降级为空。

### 4. 两层连续性门禁

确定性门禁必须检查：

- 主角和核心角色姓名是否来自 Bible，是否出现未授权变体；
- 日期是否违反时间线，地点是否可达；
- 章节开头是否消费上一章至少一个开放线程；
- 章节结尾是否兑现/推进本章 objective，并生成下一章 hook；
- 组织、资产、关系和关键数字是否与状态快照一致。

语义审查再检查因果、动机、伏笔兑现和事件合理性。语义审查失败时，状态必须进入 `blocked` 或 `needs_revision`，不能由另一个“ready”字段覆盖。

### 5. 单一发布状态

只保留一个发布裁决字段，例如：

```text
production_state: generated | needs_revision | human_approved | published | blocked
```

`published` 的唯一前置条件是：contract gate pass、continuity gate pass、human approval、artifact hash 已锁定。`publish_readiness`、`production_decision`、`final_review` 只能作为证据，不能各自拥有状态解释权。

### 6. 安全导出边界

导出器只能读取“canonical run + human_approved/published 的 chapter-final”。`produced` 仅用于内部调试，不允许生成对外书稿路径。导出前必须再次执行全书连续性检查，并输出被导出的 artifact hash 列表。

## 六、整改顺序

### P0：立即止血

1. 冻结并标记当前30章和所有导出 txt 为 `invalidated`，停止对外使用。
2. 禁止 `produced` scope 写入用户交付目录。
3. 删除/禁用多状态覆盖逻辑，建立唯一 `production_state`。
4. 对没有明确主角、年份、地点和上一章出口的项目，直接拒绝章节生产。

### P1：重建故事输入契约

1. 人工确认《重生之金融帝国》的 Canonical Story Bible。
2. 重新设计前30章，每章写出具体事件卡，不再从 conflict ladder 自动套模板。
3. 为每章生成 entry/exit contract，并建立前后章 hash 链。
4. 先只生成第1-3章做串行验收，不通过不得批量生成30章。

### P2：重建质量闭环

1. 增加姓名、时间、地点、实体、开放线程的确定性检查。
2. 将“上一章出口消费”设为硬门禁。
3. 将语义 reviewer 的失败结果映射到状态机，不再只写 advisory finding。
4. 增加跨章对抗测试：随机替换主角名、年份、公司名，门禁必须失败。

### P3：恢复批量生产

只有满足以下条件才允许跑到30章：

- 1-3章连续通过；
- 1-10章连续通过且人物/时间/地点零漂移；
- 每10章有人工 checkpoint；
- 导出前全书 hash、状态和连续性报告一致。

## 七、验收标准

整改不能以“评分提高”作为完成标准，必须满足可观察的硬条件：

1. 生成30章时，主角姓名变体数为0；
2. 核心时间线冲突数为0；
3. 未授权地点/组织/核心人物数为0；
4. 每章都有上一章 artifact hash、entry_state 和 exit_state；
5. 任一章被标记 `needs_revision` 时，后续章节不得自动生成，且不得进入导出；
6. 导出文件只包含 `human_approved/published` artifact，并带有 artifact hash 清单；
7. 故意把第2章替换成“林远泽/星耀传媒”这类异线文本时，流水线必须在确定性门禁阶段失败；
8. 从中断点恢复时，只能从 canonical run 的最后一个 approved checkpoint 继续。

## 八、最终判断

项目不是“代码全部没用”，而是最关键的生产控制架构没有兑现它承诺的能力。当前应将问题定性为：**P0 级故事状态与发布控制失效，30章产物不可交付**。

正确路线不是继续调模型、换模型或润色现稿，而是先建立唯一故事事实源、具体章节契约、严格串行状态机和 allowed-final-only 导出边界。完成这四项后，现有 registry、chapter pipeline、contract、reviewer 等模块才有继续投入的价值。
