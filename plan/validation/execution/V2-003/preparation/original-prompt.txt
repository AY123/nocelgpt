# 五、V2-003 的真正目标

V2-003 不是简单写几个 import test。

它有三个核心目标：

## A. Architecture Fitness

机器验证模块边界，确保未来 AI 写代码时不能偷偷破坏架构。

## B. Actual Diff Scope Enforcement

真实读取 Git 变化，并和当前 Task Execution Packet 的 `allowed_paths`、任务阶段和范围比较。

## C. Anti-Weakening Protection

防止 AI 为了让自己通过：

* 删除测试
* skip 测试
* 降低 threshold
* 扩大 exclude
* 删除 Gate
* 同时修改 AC + Test 让弱实现变“合法”

# 十、实际 Diff Enforcement 是本任务重点

V2-003 必须真正比较：

```text
trusted opening revision
vs
actual current worktree / commit
```

至少识别：

* Added
* Modified
* Deleted
* Renamed
* Untracked
* staged
* unstaged

不能只执行：

```bash
git diff
```

因为那会漏掉 untracked。

也不能只：

```bash
git status --short
```

然后完全依赖文本解析而不核对内容。

---

# 十一、Diff 必须绑定 Execution Packet

每一项实际改动必须映射到：

```text
allowed_paths
```

或者明确的已授权例外。

必须检测：

```text
exact file
directory scope ending in /
resolved path
symlink
rename source
rename target
delete path
```

。

防止：

```text
allowed: src/anovel/domain/
actual: src/anovel/domain/../../gateway/x.py
```

这类路径绕过。

---

# 十二、但路径 PASS 不代表业务语义 PASS

这一点必须明确保留。

例如：

```text
allowed_paths:
  tests/
```

AI 在 tests 里删除 80% 断言：

```text
path scope = legal
semantic governance = illegal
```

所以 Diff Scope 和 Anti-Weakening 是两个独立检查。

不得：

```text
路径在 allowed_paths
→ automatically approve
```

。

---

# 十三、必须区分 pre-existing user changes

如果任务开工前已经存在：

```text

```

或其他用户改动：

必须记录 opening snapshot。

后续 Diff Review 中：

```text
pre-existing change
!=
V2-003 produced change
```

AI 不得：

* reset
* checkout
* revert
* delete
* silently stage
* include in V2-003 evidence

来制造干净工作区。

# 十四、AT-V2-003-04：实际范围负例

至少必须有这些测试：

### 合法新增

```text
allowed path
+ new file
→ PASS
```

### 合法修改

```text
allowed existing file
→ PASS
```

### 合法删除

仅当该 Task 明确允许此删除：

```text
→ PASS
```

否则：

```text
→ FAIL
```

### 合法 rename

如果 source + destination 均符合授权：

```text
→ PASS
```

### 越界新增

```text
new src/anovel/future_feature.py
not allowed
→ FAIL
```

### 越界修改

```text
other task file changed
→ FAIL
```

### 越界删除

```text
delete unrelated test
→ FAIL
```

### Untracked

未跟踪文件同样必须纳入范围。

不能：

```text
untracked
→ ignored
```

### Empty scan

如果 scanner 因 bug 没看到实际 diff：

```text
→ FAIL
```

不能把：

```text
0 changes checked
```

冒充完整覆盖。

# 十五、AT-V2-003-05：Anti-Weakening

必须把**可信开工基线**和本次变化比较。

至少识别这些类别：

```text
acceptance criteria deletion
scenario deletion
scenario assertion weakening
test file deletion
test function deletion
skip
xfail
threshold decrease
scan exclusion increase
allow_failure introduction
required check removal
Gate removal
minimum baseline reduction
validator weakening
```

。

不要只搜索几个固定关键词。

应该尽可能结构化比较。

---

# 十六、重点防“同步降标”

这是本任务最关键的攻击模型之一。

例如 AI 同时修改：

```text
implementation-backlog.yaml
test-catalog.yaml
test file
```

使三者重新一致。

普通一致性 validator 可能 PASS。

但 V2-003 必须检测：

```text
旧基线要求：6 个场景
新基线要求：5 个场景

机器源一致
测试也一致

但 requirement 被削弱
```

结果必须：

```text
BLOCK / REQUIRE EXPLICIT AUTHORIZATION
```

而不是：

```text
everything consistent
→ PASS
```

。

---

# 十七、测试 skip 必须特别处理

识别至少：

```python
@pytest.mark.skip
@pytest.mark.skipif
pytest.skip(...)
unittest.skip
```

以及项目实际测试框架中等价行为。

新增 skip 不一定永远非法。

但必须要求：

```text
reason

impact

```

否则不能自动通过。

# 十八、Threshold / Exclusion 变化



```text

```

# 十九、合法规则修订也必须能通过

Anti-Weakening 不能退化成：

```text
任何测试/规范变化都 FAIL
```

必须有正例。

例如：

### 新增测试

```text
5 scenarios → 6 scenarios
→ PASS
```

### 等效重构

改变测试代码组织：

```text
requirement unchanged
coverage unchanged
→ PASS
```

### 合法规则修订

如果确有：

```text
explicit authorization
change reason
impact analysis
replacement verification
```

则允许。

但关键原则：

> 实施 AI 自己写一句“这是合理修改”不能成为批准依据。
