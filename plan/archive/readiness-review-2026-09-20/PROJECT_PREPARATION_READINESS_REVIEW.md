这不是要求继续扩大研究范围。当前需要的是修正既有规范、落实首批任务、运行工程门禁。继续生成另一套总体架构，只会增加需要同步的来源。

## 3. 已经充分的准备，应予以保留

### 3.1 项目方向与范围控制

从“多 Agent 生成文本”转向“受约束、可追溯、可修复的连续叙事生产系统”，方向正确。单章、双题材 10 章、双题材 30 章、100 章、300+ 章的递进能够逐步暴露不同风险。

Reference Intelligence、Corpus Learning、复杂市场反馈留在稳定内核之后，避免高级功能掩盖基础事务和题材隔离问题。模块化单体、暂缓微服务/Kafka/强制 K8s/图数据库/常驻角色 Agent，也适合当前验证目标。

### 3.2 双 Anchor 的选择

`urban.business.realistic` 与 `fantasy.eastern.progression` 差异足够明显，适合检验通用叙事模型与题材扩展的边界。选择双 Anchor 的价值在于检验同一内核能否表达不同世界规律，而不是证明两个文件存在或一次生成没有禁词。

Genre 在架构上是一等概念，并不要求把 Genre 实现阶段挪到 Narrative/Canon 前。领域内核应从一开始避免写死题材，但执行顺序仍应遵循已经冻结的 P1 Narrative、P2 Canon、P3 Genre。

### 3.3 V1 经验已经被系统整理

现有资料覆盖失败继续执行、Canon 旁路、重复提交、上下文混用、评分越权、硬编码合约、密钥与测试治理等问题。V1 不整体迁入 V2、优先保留失败样本和领域经验的方向已经明确。

新增 [V1_REUSE_DECISION_MATRIX.md](../V1_REUSE_DECISION_MATRIX.md)、[V1_REGRESSION_ASSET_REGISTER.md](../V1_REGRESSION_ASSET_REGISTER.md) 和 [CCDOC_ADOPTION_MATRIX.md](../CCDOC_ADOPTION_MATRIX.md) 是实质进展。尤其是把 ccdoc 拆分为 ADOPT/ADAPT/DEFER/REJECT/HISTORICAL，有助于阻止候选示例成为默认规范。

### 3.4 核心边界与失控停止规则

Draft ≠ Canon、Plan ≠ Canon、Workflow State ≠ Canon State、模型输出只是提议、Canon 唯一提交入口、Permit 受控签发、先补丁后全量重写，这些原则值得保留。

Canon 损坏、真实密钥泄露、重复提交、跨项目泄漏、硬门禁绕过和第二 Canon 写入路径触发冻结新功能，也应保留。后续需要把事故识别和恢复证据落到测试与流程中，而不是重新讨论原则是否必要。

### 3.5 治理资料已经建立，问题从“缺文件”转为“文件是否一致”

现已有来源清单、规范索引、术语表、权责矩阵、数据所有权、Artifact 生命周期、风险登记、ADR 登记、任务注册表和就绪报告。因此不再接受“再补一个索引就准备完成”这样的判断；应检验这些文件能否共同给出唯一实施答案。

## 4. 仍不能认定全面完成的关键问题

### RR-01：新规范索引仍指示旧实施顺序

**证据：**[NORMATIVE_INDEX.md](../.claude/convergence/NORMATIVE_INDEX.md) 第 102、111～113、514 行仍写 `Genre → Domain → Canon`、P1 Genre、P2 Domain、P3 Canon。第 135～140 行又把 V2-011/012 当 Planning、V2-013～015 当 Context。当前机器任务表中这些编号分别属于 Canon 和 Genre。

[DATA_OWNERSHIP_MATRIX.md](../DATA_OWNERSHIP_MATRIX.md) 第 17 节和 [AUTHORITY_MATRIX.md](../.claude/convergence/AUTHORITY_MATRIX.md) 的实施门槛表保留类似错位。后者仍写 `P1 (Genre Foundation)`。这说明改正注册表和就绪报告的局部内容，没有消除其他规范性指令。

宪章与实施计划中的 M 编号也仍存在旧冲突。例如宪章 M7 表示 100 章，而实施计划 M7 表示 30 章。规范索引缺少足够明确的逐项替代关系。

**后果：**不同开发者或模型读取不同入口，会选择不同实施顺序、错误任务和不同验收时间。

**最晚关闭：P0 基线冻结前。**保留用户冻结路线；任务身份从 backlog 生成；阶段与里程碑有唯一映射；旧引用纠正或明确降为历史。验证器应检查所有现行规范，不只检查一份就绪报告。

### RR-02：证据编码仍混用来源、可信度和权限

**证据：**宪章中 E0 是确定性证据、E1 是结构化抽取、E3 是人工 Gold/盲评、E4 是真实市场；新 [TERMINOLOGY_BASELINE.md](../.claude/convergence/TERMINOLOGY_BASELINE.md) 第 44、207 行改为 E1 确定性、E3 模拟读者；[DATA_OWNERSHIP_MATRIX.md](../DATA_OWNERSHIP_MATRIX.md) 第 580 行又把人工 Golden Set 标成 E4。[ARCHITECTURE_RISK_REGISTER.md](../ARCHITECTURE_RISK_REGISTER.md) 前部 E3 是人工，后部又写 human/sim。

冲突登记把 Evidence 同名对象的重命名标为 RESOLVED，并未解决这些编码语义差异。将名字改成 ConfidenceLevel 也不能自动解决它。

**后果：**模拟评价可能被当成人工校准，抽取结构合法可能被当成叙事事实真实；权限策略会在错误证据上运行。

**最晚关闭：P0 冻结术语，P7 验证实际执行。**需要唯一编码版本，并把 `source_kind`、校验状态、校准引用和权限范围分开。不能把确定性代码验证与读者偏好放到一个“数字越小越真”的通用序列里。

### RR-03：“12/12 PASS”与“97.5% 完成”缺乏足够可靠的依据

[convergence-validation.json](../.claude/convergence/convergence-validation.json) 声称 60 任务全量通过，但其阶段计数之和是 **56**。

| 阶段 | 记录中的数量 | backlog 实际数量 |
|---|---:|---:|
| P6 | 2 | 3 |
| P7 | 6 | 9 |
| P8 | 4 | 8 |
| P9 | 5 | 1 |

注册表生成器本身输出正确；错误在验证结果记录及其覆盖范围。生成器没有承担整个规范树的矛盾检查。

验证记录仍引用当前树中不存在的 `CONVERGENCE_CORRECTION_SUMMARY.md`。就绪报告仍把 `GPTDOC_CONFORMANCE_AND_DEFECT_REGISTER.md` 和 `BOUNDARY_SEPARATIONS_VERIFICATION.md` 列为 COMPLETE，却没有可用的当前文档路径。这些文件可能曾存在于历史提交；删除过渡文件不必然错误，但当前证据必须迁移或明确指向可复核的历史版本。

同一就绪报告第 183 行建议把 Genesis Bootstrap、Provider UNKNOWN 放进 P0，第 428～429 行又正确推迟到 P2/P5/P6。对应“P0 已净化”校验没有覆盖全文。

**最晚关闭：P0 基线冻结前。**校验结果应由真实校验程序生成，绑定输入哈希、提交、工具版本和规则范围；不能由静态 PASS 字段自证。无清晰分母与权重的 97.5% 不应继续作为放行依据。

### RR-04：任务目录尚未成为执行契约，阶段门槛还不能自动阻止越级

机械复核结果：60/60 任务只引用宪章；60/60 的 `artifacts` 和 `out_of_scope` 为空；测试引用仍是 `TEST-V2-NNN`。三条通用验收不能告诉实施者具体应产生什么、如何证明正确。

V2-005 的依赖只有 V2-001。稀疏任务 DAG 本身不是错误，可以配合独立阶段 Gate 使用；问题在于当前没有可执行的检查来确保 V2-002～004 及 P0 退出证据完成后才进入 P1。任务 Schema 仍接受没有测试与验收证据的 CLOSED 对象。

**最晚关闭：P0 首批任务启动时补足其执行信息；每个后续任务启动前滚动补齐；P0 退出前建立 Gate 规则。**不要求立即把 60 个任务全部细化到实现级别，但 V2-001～004 必须具体化，P1 的输入/接口决策也必须具备明确归属。

### RR-05：ADR 已登记，但部分归属仍指向错误任务

[REQUIRED_ADR_REGISTER.md](../.claude/convergence/REQUIRED_ADR_REGISTER.md) 第 476 行后的表将 Provider Gateway 指向 V2-027、Context 指向 V2-013、Workflow 指向 V2-017、Patch Repair 指向 V2-023。正确任务身份分别应核对 V2-019、018、020、031 等相关项。

Promise 和 Event 的决策集中绑定 V2-006，但任务表将相关核心安排在 V2-007；扩展命名空间绑定 V2-008，实际 Genre Kernel 是 V2-013～016。任务本身还不能代替具体责任人/实施角色和决策记录。

**最晚关闭：P0 纠正归属；在相应接口首次实现前作出必要决策。**角色/事件/时间/未知值等影响基础模型的决定应在 P1 相关任务内部先定再写；不需要等所有 28 个 ADR 都定稿才启动 P0。

### RR-06：新治理文本没有替代旧机器契约缺陷

本次复跑仍确认：

- 合法 Character 扩展字段会被基础 Schema 拒绝，错误实体类型反而可通过 Character Schema。
- 缺少路径/值/证据的操作、未注册操作可通过相关 Schema。
- 空验证引用的 ALLOW、全空质量层的 PASS、Q0 HARD_FAIL 与 PASS 并存可通过结构验证。
- 空用例/指标的认证 PASS、无验收证据的 CLOSED 可通过结构验证。
- Provider 在没有响应时失败，仍无法满足必填 response_hash。

某些约束应由领域服务和数据库而不是 JSON Schema 承担；不能据此推断 Schema 通过就有放行权。问题在于应明确哪一层负责、如何调用和如何检验拒绝路径。

**最晚关闭：按 P1/P2/P5/P7/P8 相关任务；治理类 CLOSED 约束在 P0。**原资料可以保留历史快照，但进入实施的现行接口必须经修订及正反例验证。文字上将问题“绑定 ADR”不是问题已经解决。

### RR-07：证据保留策略与永久追溯目标冲突

[DATA_OWNERSHIP_MATRIX.md](../DATA_OWNERSHIP_MATRIX.md) 规定 CanonCommit 永久保留并引用 permit ID，却规定 CommitPermit 提交后删除、不能重建。ChapterContract 六个月、SceneContract 三十天、Context 示例九十天后删除，也没有完整规定已接受章节的证据闭包如何保留。

**后果：**以后只有哈希和 ID，可能无法重放检查“当时为何允许提交”。重新调用编译器不等于重建历史输入；模型、政策和依赖版本可能已经改变。

**最晚关闭：P2 设计 Canon 收据及保留策略时，P4/P5 接入各类 Artifact 时验证。**失效 Permit 不应再有执行权，但历史授权记录可以保留。接受提交需保留足够的不可变证据，或持有内容完整、能够独立核验的长期收据。缓存的删除期限与审计证据的保留期限应分开。

### RR-08：哈希与重试定义还不够精确

[ARTIFACT_LIFECYCLE_REGISTER.md](../.claude/convergence/ARTIFACT_LIFECYCLE_REGISTER.md) 已补充 Envelope、序列化和操作代数，是进步。但小数“语义所需最小精度”、指数“语义需要时允许”仍无法唯一确定字节。正文原始字节、归一化文本与结构化数据也需要分别定义身份。

[ARCHITECTURE_RISK_REGISTER.md](../ARCHITECTURE_RISK_REGISTER.md) 第 253 行把 attempt_id 放进幂等键。若每次重试产生新 attempt_id，就会产生新键，失去重试去重效果；除非规范把这个字段明确限定为跨重试稳定的逻辑标识。

**最晚关闭：哈希/逻辑请求身份在 P2，Provider 语义在 P5/P6。**给出相同语义不同编码的固定测试向量、同键同载荷返回同收据、同键异载荷冲突、CAS 失败语义，以及稳定 logical request 与 execution attempt 的区别。

### RR-09：P0 工程产物尚未出现，文档完成不能替代工程验收

当前已有本地 Git 仓库，但还没有检出目标 V2 的 `pyproject.toml`、锁文件、`src/`、`tests/`、实际 CI 配置及 Compose 测试环境。根目录 README 仍主要是仓库平台初始说明。`PHASE_0_REPOSITORY_BOOTSTRAP_EXECUTION.md` 也尚未在当前树中发现。

这并不阻止开始 P0：上述恰好是 P0 需要交付的工作。它阻止的是宣布 P0 已绿色，或把“已有仓库”误作“工程仓库已完成”。

**最晚关闭：P0 退出。**至少应有干净环境可复现的安装/测试命令、固定依赖、模块边界检查、实际密钥与依赖门禁、PostgreSQL 测试环境以及当前提交的 CI 证据。

### RR-10：V1 回归“登记”尚未成为可执行资产

现有登记表提供了较完整的失败模式目录，但其中的测试名称和测试要求不能自动视为已存在的 V2 测试。复用矩阵把 23 条目录项写成“23 V1 test failures”，也容易与实际历史测试执行数量混淆。

**最晚关闭：P0 转化安全/架构边界回归；其余随对应任务转化。**每条资产应有稳定编号、原证据、可复现输入、预期结果、目标测试路径和执行结果。未转化项标记为 PLANNED，不应写 VERIFIED。不能把 23 条风险目录、历史失败测试数与新执行用例数混为一个统计值。

### RR-11：双 Genre 认证还需要明确证据协议

现有规划已认识到关键词规则不足、GenrePack 文件不等于支持 Genre，但具体样本、世界规则、合法交叉表达、遗漏检测和认证报告仍需变成执行协议。

都市里“公司现金流断裂”与“公司灵气枯竭”需要不同判断；小说中人物讨论玄幻、梦见修炼或使用比喻，不自动等于现实世界增加超自然能力。玄幻世界中的交易、商会、财富，也不自动等于被现代商业 Schema 污染。规则应判断世界事实及适用语境。

**最晚关闭：P3 确定双 Pack 边界和正反例；P8 前冻结认证协议。**P8/P9 认证同时报告自然生成与故障注入、误报/漏报/弃权、正文覆盖、抽取遗漏、Canon/Workflow 一致性、版本与成本。不能把被模型筛掉的失败稿从样本分母里删除。

### RR-12：自动化、可读性和市场目标的验收仍需操作化

资料已经覆盖人工介入、市场信号、Golden Set 和盲评，因此不再说“完全没有产品验证设计”。尚缺的是早期可执行的测量协议及实际样本。

“能连续提交 30 章”“读者愿意继续读”“在真实平台环境中获得商业成绩”是不同结果。前者必要，但不足以证明后两者；模拟读者分数也不能直接替代真人或市场。

**最晚关闭：P5 前成本与介入日志口径；P8/P9 前最小真人文本验收；P11/P13 再升级校准与市场实验。**不必为早期人工读稿提前建立整个学习平台。

## 6. 面向“自动写出爆款”的准备必须如何衡量

### 6.1 三条证据链分别验收

**生产可靠性：**错误状态不进入 Canon，支持恢复，题材和项目不混用，正文/合约/上下文/提交证据一致。由确定性检查、数据库集成、故障注入和连续生产报告支撑。

**阅读竞争力：**人物目标清楚、选择有代价、冲突有因果、承诺得到兑现、节奏有变化、中文表达自然、读者有继续阅读动力。由文本样本、真人评阅和同条件基线比较支撑；不能把每章爽点数量、突破频率或机械评分当成普适真理。

**市场结果：**真实读者获取、后续阅读及商业表现。需要真实平台或可说明边界的读者实验数据。架构不能预先保证这一结果，也不应因此取消该目标，而应把它保留为最终产品验证。

### 6.2 两个最值得提前准备的小型实验

1. **同条件生产对照。**用相同题材、故事输入、长度目标和可说明的模型/预算条件，比较简单生成基线与完整管线。保留全部尝试和人工介入；比较接受章节成本、严重事实/题材错误、读者偏好及继续阅读行为。用于判断新增复杂性究竟改善了什么。
2. **双题材边界样本。**同时包含真实污染、合法引用/梦境/比喻、未明确事实、抽取遗漏和修复后回归。不能只有明显禁词负例，也不能只有“正常稿全部通过”的正例。

这两项可以在 P3～P8 逐步完成，不应转化成 P0 的大规模语料、爬虫、市场趋势平台或模型训练项目。

### 6.3 自动化与成本必须把隐藏劳动纳入

至少记录：每次任务运行、请求与重试次数、候选/接受字数、废稿与修复、模型费用、UNKNOWN 待核费用、人工改稿字数、人工介入分钟数、介入原因和最终接受章节。

“每章成本”分母应是被接受的章节；“自动完成率”需同时披露人工介入。只能展示成功章节会掩盖系统的实际可靠性与经济性。

提前确定首个使用场景（例如本地单人内部生产还是多用户服务）、负责人、实际运行环境、模型预算边界，有助于 P0/P5 做选择。当前审核没有足够证据替用户假定全部部署和商业参数；这些是实施决策，不需要再写一份宏观研究。

## 7. 最小收敛与 P0 执行建议

### 7.1 先修正现有控制资料

在 V2-002 范围内完成：统一阶段/里程碑/术语；纠正 ADR 和风险归属；对旧资料标明历史或被替代关系；修复失效证据引用；由程序生成真实验证结果。无需新增平行权威来源。

缺陷状态建议区分“已识别”“已分配”“已修订”“已验证”“已关闭”。缓解策略已写好，只能说明已经有应对方案；不能直接标为风险已消除。

### 7.2 四个 P0 任务必须交付的实际结果

| 任务 | 应交付 | 必须看到的验收证据 |
|---|---|---|
| V2-001 Repository bootstrap | V2 包骨架、运行版本、锁文件、开发命令、PostgreSQL 测试环境、有效 README | 干净环境按命令可安装；最小测试可运行；DB 环境可连接和清理 |
| V2-002 Normative index | 唯一规范入口、冲突与替代关系、正确任务/阶段/里程碑映射、首批任务验收信息 | 注册表再生成无差异；错位引用会失败；CLOSED 缺证据被拒绝 |
| V2-003 Architecture fitness | 导入/写入权责等初始边界检查框架 | 合法最小结构通过；故意违反边界的夹具失败；未来规则有启用阶段 |
| V2-004 Security/dependency CI | 实际 CI 文件、密钥扫描、依赖检查、相关必过任务 | 当前提交 CI 结果；适用硬门禁失败能阻断；结果不是文档截图或手写 PASS |

`PHASE_0_REPOSITORY_BOOTSTRAP_EXECUTION.md` 可以作为这一轮的执行文件，内容限定为上述四项、现行规范入口、命令、产物路径、负责角色和证据要求。

### 7.3 P0 绿色不应靠提前实现整个系统，也不能靠跳过测试

P0 不实现 Genesis 业务、Provider Gateway、完整 Q0–Q3、30 章认证。其 CI 应验证当前阶段真实产物，并明确未来检查的启用门槛。未实现的阶段标为 NOT_APPLICABLE/NOT_IMPLEMENTED，并带理由，不能标为 PASS。

原始 gptdoc/ccdoc 可以作为不可变历史资料保存；当前启用的规范、Schema 和测试必须有明确清单。把已知失败的业务契约藏进被跳过的测试，再宣称这些契约通过，不符合绿色验收；同样，强迫 P0 一次实现所有未来业务也违反冻结范围。

PostgreSQL 环境与最小集成门禁可以在 P0 建立，Canon CAS/幂等的真实业务集成测试在 P2 随代码启用，启用后必须硬阻断。真实 Provider 测试应在 P5 后及认证/发布节点取得证据，不能永远只跑 Mock，也不需要 P0 先调用真实模型。

### 7.4 P0 退出到 P1 的放行

应同时具备：首批四任务的代码/配置、针对其产物的测试、当前提交 CI、验收证据；控制基线没有未裁决的冲突；V2-005 具备具体输入和验收边界。

P1 的 Schema 修正可以在 P1 相关任务中完成。P2 的根提交引导可以使用明确的测试/人工初始输入，经同一提交服务进入 Canon；不能为了提前测试而开放生产旁路，也不需要将完整 P10 Genesis 提前。

## 9. 最终判断

准备工作已足以让项目进入实施，而且继续扩大总体研究的边际收益很低。但现状还不能被称为“全面完成的、无歧义的、已经验收的架构基线”。

最值得立即投入的工作，是把现有丰富资料收敛成可执行的 P0，纠正治理文档自身的冲突，并用真实测试和 CI 建立可信的完成标准。此后按阶段修正机器契约、证明单章可靠、双 Genre 10 章稳定、30 章持续一致，再推进高级智能。

**审核建议：启动 P0；暂不确认当前 BASELINE_FREEZE 已通过；P0 验证完成后再进入 V2-005。**
